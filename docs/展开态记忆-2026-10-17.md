# 展开 / 收起状态记忆：回到主页保留最后一次操作（2026-10-17 · 第 18 轮）

用户原话：「对这个聚合的展开与收缩进行一个记忆，回到主页的时候留存我最后一次的操作，
而不是直接全展开或者全收缩起来」。

验证：tsc 0 错；vitest **30 文件 / 557 用例**（基线 536，+21）；
`cargo test` **562 / 0**（基线 557，+5）；`cargo check` 警告 0；分层合规通过；`vite build` 成功。

---

## 一、根因：封面墙会被**卸载**，展开态随组件一起被销毁

`App.vue` 里封面墙挂在一个 `v-if / v-else-if / v-else` 链的**最后一个分支**上：

    <MediaDetail   v-if="media.selectedId && !inSettings" />
    <SettingsPanel v-else-if="inSettings" />
    <LibraryCatalog v-else-if="inCatalog" />
    <PosterGrid    v-else />      ← 点开详情页就走到第一个分支，封面墙被**卸载**

`expanded` 与 `collapsedByUser` 都是组件内的 `ref`，组件一卸载就没了。返回主页时组件**重建**，
而「新分组自动展开」那段 `watch` 带 `immediate: true`，于是又把所有分组摊开 ——
用户看到的正是「我上次明明收起来了，回来又全开了」。

⚠️ 顺带说明为什么**不能**靠 `keep-alive` 或把 `expanded` 提到 `App` 了事：
前者会连带保住详情页滚动位置等一堆不相干状态；后者只是把同一份内存状态挪个地方，
**仍然活不过应用重启**，而用户要的是「回到主页」乃至下次打开还在。所以落库是正解。

---

## 二、改法

### 1) 新增持久化字段 `collapsedGroups`（只记折叠，不记展开）

Rust `Settings` 加 `collapsed_groups: Vec<i64>`（`#[serde(default)]`，前端键 `collapsedGroups`）。
settings 是 KV 表，新增 key 即生效、**不需要迁移**（B6）。读侧脏值回落空数组，不报错。

🔑 **为什么只存"折叠"的、不存"展开"的**：展开的分组会随扫描 / 拖动不断新增，
存「展开」等于存一份**只会变长**的名单，而且条目被删后越来越脏；
折叠天然是少数派，语义也正是「用户明确否决了自动展开」——与组件里 `collapsedByUser` 同一个意思。

### 2) 组件仍无 store 依赖：走 prop 进、事件出

    <PosterGrid
      :collapsed-groups="settings.collapsedGroups"
      @collapsed-change="settings.setCollapsedGroups" />

与上一轮的 `manualOrderGroups` 保持一致（封面上要能单独 `mount(Grid, { props })` 测试）。
上报的是**完整**折叠名单（不是某一项）：组件内部真正的真相来源是 `expanded` 这个 Set，
整体交出去最不容易与父级那份状态失配，也天然处理了「一键展开后名单应清空」。

### 3) 初值必须在 setup 期间就位（本任务最隐蔽的一处）

    const collapsedByUser = ref<Set<number>>(new Set(props.collapsedGroups ?? []));

⚠️ **不能**等后面那个 watch 去补：紧跟着的「新分组自动展开」watch 带 `immediate: true`，
setup 期间就会跑一遍。那一刻若 `collapsedByUser` 还是空的，它会先把用户亲手收起的分组
统统摊开 —— 再补就晚了，因为"他收过"的证据已经被自己抹掉。
**这正是本缺陷最容易被改错的地方。**

### 4) 时序竞争：设置是**异步**加载的

`App.onMounted` 里的设置 IPC 是异步的，封面墙很可能**先挂载**、`collapsedGroups` 后到。
若无条件接受后到的 prop，用户在设置到达前做的那次折叠会被一个更旧的库值覆盖
（表现："刚收起来又自己开了"）。所以加一个 `userTouched` 标志：**用户一旦动过手，就以本地为准**，
不再接受外部回填。

### 5) 上报时过滤掉"已经不存在的分组"

    groups.value.filter((id) => !expanded.value.has(id))

折叠名单会跨会话留着。某个分组**被删掉**（或本次筛选下不可见）后不该继续占着名单，
所以只上报「当下真实存在且收着的」—— 名单才不会越积越脏。

### 2) 🔑 变异测试（两处，都证明用例有牙齿）

**变异 A —— 摘掉组件侧的记忆读取**（`new Set(props.collapsedGroups ?? [])` → `new Set()`）：

    × 传了 collapsedGroups=[1]：挂载时那一组就是收着的
    × 传了 collapsedGroups=[1,2]：两组都收着
    × 折叠 A 后离开再回来：A 仍然是收着的（不会被自动展开冲掉）
    × 一键收起后离开再回来：仍然全是收着的（而不是全展开）
    × 上报的折叠名单只含当下存在的分组
    Tests  5 failed | 5 passed (10)

**变异 B —— 破坏 App 侧接线**（`:collapsed-groups="settings.collapsedGroups"` → `"[]"`）：

    × 把 settings.collapsedGroups 传给封面墙
    × 切到目录库再切回「全部」：封面墙重建后仍带着折叠名单
    Tests  2 failed | 10 passed (12)

两处都**恰好**只打中与"记忆"直接相关的用例，其余不受影响 → 用例钉的是行为，不是实现细节。

### 3) 核心用例的构造手法

「离开再回来」在单测里就是 **`unmount()` 之后用同一份上报的名单重新 `mount`** ——
那正是用户来回切页面时真实发生的事，也是原先丢状态的那一步。
直接断言"卸载前收着"是不够的，必须断言**重建后仍然收着**。

### 4) 向后兼容（查了真实库）

用户库里 `collapsedGroups` = **None**（没这个键）→ 前端读到 undefined → 空数组 →
全部默认展开，**与升级前行为完全一致**，不会让老用户一升级就看到满屏收起来的分组。

## 五、遗留与取舍

1. 折叠名单是**按分组 id**记的，不区分视图 / 筛选。同一个分组在不同筛选下当然还是"收着"，
   这符合直觉；但若将来给分组引入"文件夹"以外的语义，需要重新考虑。
2. `setCollapsedGroups` 在值未变时**不发请求**（列表刷新会频繁触发）；
   这会让"落库"稍微延迟到下一次真实变化 —— 但既然值没变，落不落都一样。
3. **按约束没有启动 exe**：结论来自单测 + 两处变异测试 + 真实库兼容性核对。
4. 本轮仍未 `git add`。
