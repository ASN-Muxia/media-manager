## 1. 需求原文（逐字引用）

> 为列表增加可选的排序规则功能：提供明确的排序方式切换入口（按名称首字母/拼音排序、按时间排序，时间排序需说明以添加时间还是上映/首播时间为准，并支持正序/倒序）。排序时，无法被识别为电影或剧集的条目（类型未知或缺少元数据）统一排在列表末尾，未识别条目内部仍按当前所选规则排序。切换排序方式后列表应立即重新排序，其余展示逻辑与交互行为保持不变。

## 2. 产品目标（一句话）

> 让用户能用一个明确的入口，按「名称（拼音）」或「时间」对媒体列表正序 / 倒序排序，并保证「类型未知或缺少元数据」的条目始终沉到列表末尾、其内部仍按当前规则有序，从而把真正可看的影视排在前面。

## 3. 用户故事

| # | 用户故事 |

| US1 | 作为**影视库使用者**，我希望按片名拼音 A→Z 浏览列表，以便像音像店货架一样快速定位某部片子，而不用在几千条里翻找。 |
| US2 | 作为**刚批量导入一批新资源的用户**，我希望按「添加时间 · 倒序」排序，以便一眼看到这次新进了哪些条目并优先刮削它们。 |
| US3 | 作为**想按年代回顾的用户**，我希望按「上映 / 首播年份」排序，以便把同一年代的片子聚在一起连续看。 |
| US4 | 作为**库里混着大量未识别文件的用户**，我希望这些「判不出是电影还是剧集、或没有年份 / 标题」的条目统一沉到列表末尾，以便前排全是有效资源，不用在有效条目里被噪声打断。 |
| US5 | 作为**老用户**，我希望我选的排序方式下次打开还在，以便不用每次启动都重新点一遍。 |

## 4. 排序语义定义（本次 PRD 的核心，工程实现的唯一契约）

### 4.0 通用约定

- 排序**只作用于封面墙 / 列表视图（`PosterGrid`）**，即 `mediaStore.visibleItems()` 的返回值。
  **不**改变：`SeriesTree`（层级视图自带顺序）、`CollectionPanel`（合集内已按上映时间排）、`MediaDetail`、`Sidebar` 栏目列表、后端 `get_media_list` 的默认 `ORDER BY`。
- 「其余展示逻辑与交互行为保持不变」：排序**不**改字段、**不**改筛选口径、**不**改选中 / 全选 / 反选 / 刮削所选 / 删除所选的语义（这些操作一律作用于**排序后的可见列表**，顺序即用户看到的顺序）。
- 比较必须是**全序且稳定**：任何两条条目都不能「相等后随机摆放」。统一兜底链：
  `排序键 → 名称键（见 4.1）→ id 升序`。
- **补 D7（架构补齐，PM 确认）**：**先排序、后按关键字过滤**（`orderedItems` computed → `visibleItems()` 在其上做 O(n) 过滤）。排序是全序，子集结果与全集一致；这样敲关键字只过滤、**不重排**。
  > 附带工程要求（架构实测）：`visibleItems()` 在一次渲染里被调用 7 次（模板 4 次 + store 内部 3 次），排序**必须**落在 `computed` 里靠缓存，不能写进 `visibleItems()` 函数体，否则一次渲染跑 7 遍全量排序。

### 4.1 名称键 `nameKey(item)`（按名称首字母 / 拼音排序）

**取串优先级**（取第一个非空者，trim 后为空视为空）：
`display_title` → `title` → `original_title` → `file_name`（去掉扩展名）。
> 理由：`display_title` 就是用户在卡片上看到的字，用它排才不会出现「看到的字和排出来的位置对不上」。

**归一化**：`String.prototype.normalize("NFKC")` → 再 NFD 并去掉组合记号（把 `é` 折成 `e`）→ `toLowerCase()`。

**权重流生成**：逐码点扫描，映射为「类别 + 比较串」：

| 字符类别 | 判定 | 类别序 | 参与比较的内容 |
|---|---|---|---|
| D 数字 | `0-9`（全角数字先经 NFKC 折成半角） | 1（最前） | 原字符 |
| L 拉丁字母 | `a-z` 及已去重的拉丁派生字母 | 2 | 折重音后的小写字母 |
| P 汉字 | CJK 统一汉字（U+3400–U+4DBF、U+4E00–U+9FFF、U+F900–U+FAFF、U+20000–U+2FA1F） | 3 | **该汉字的拼音秩**（由 D 档 ICU 产出，见下方「拼音怎么落地」；**含声调序**，PRD 原「无声调」表述已作废） |
| O 其它文字 | 日文假名 / 汉字以外的东亚文字 / 西里尔 / 希腊等 | 4（最后） | 原码点 |
| — | 空白、标点、符号、Emoji、括号、`·` 等 | 不参与 | **跳过**（不参与比较） |

**比较规则（两级）**：
1. 一级：先比**类别序**（D < L < P < O），类别不同即定序；类别相同再比该类别内的比较串字典序。
   → 这就是中英混排的确定答案：**数字开头最前，其次纯英文，再次中文（按拼音），最后其他语种**。
2. 二级：权重流完全相同 → 按 `year` 升序（NULL 视作最大）→ 按 `id` 升序。

**数字开头怎么算**：数字归 D 类，排在所有字母与汉字**之前**；数字内部**按字符逐位比较**（即 `"10"` 在 `"9"` 之前，不做数值解析）。
> 理由：标题绝大多数不是纯数字，做数值解析要引入「第10集 / 1080P / 2 Fast 2 Furious」之类的歧义；按字符比是确定、可测、无歧义的。（自然序作为 P2 可选项。）

**正序 / 倒序**：正序 = A→Z（权重流升序）；倒序 = Z→A（权重流降序）。

#### 拼音怎么落地（**已决断：D 档**）

> **变更记录（2026-10-07，架构决断，PM 已复核确认）**：原 A 档（静态全拼表）/ B 档（首字母桶）**均已否决**，改为 D 档。

| 档 | 方案 | 做法 | 状态 |
|---|---|---|---|
| A 档 | 静态全拼表（6763+ 字常量，约 100KB） | 内置 `pinyin-data.ts` | ❌ **否决**：本机**无任何离线拼音数据源**（无 pypinyin、node_modules 无拼音包），字表只能联网抓取生成 → 引入「构建期联网」隐性依赖，与 C11 / B2 冲突；且涉及数据源许可（kTGHZ2013 为 CC-BY-SA）；产物是无人能核对的手写常量 |
| B 档 | 首字母桶 + 桶内码点 | 内置首字母表 | ❌ **否决**：相对 A 档只省体积、**不省生成工序**，收益更差，不值得单列 |
| **D 档（采用）** | **ICU / CLDR 内置 zh 拼音** | `new Intl.Collator("zh")`：ECMAScript **标准库**，随 Node / Chromium 的 ICU 分发 —— **不是依赖、不是数据表、不需要联网**。CLDR 中 `zh` 的默认 collation 就是 pinyin（注意：`zh-Hant` 是 stroke，别用） | ✅ **采用** |
| C 档（降级） | 纯 Unicode 码点 | ICU 自检失败时回落 | ✅ 保留为**降级路径**（= 升级前行为，无回归，不崩不乱序） |

**D 档的三个已知边界（PM 判定：全部接受）**：

| 边界 | 实测 | PM 判定 |
|---|---|---|
| **声调参与排序**（PRD 原文写「无声调」） | `妈 < 马 < 骂` | ✅ **接受，PRD 原文「无声调」作废**。ICU 声调序（阴平→阳平→上声→去声）稳定且可解释；它只是让原本要靠 `id` 兜底的同音字获得确定顺序，反而更贴合 §4.0「全序且稳定」。PRD 的真实诉求是「不出现用户无法理解的顺序」，声调序满足该诉求 |
| **多音字** | `长` 取 `zhang` | ✅ 接受。CLDR 按常用读音取舍，与任何静态表等价。用户自定义覆盖仍放 P1-4 |
| **无「表外汉字」概念** | 拼音秩用**当前列表里实际出现的汉字**构建 | ✅ 覆盖率恒为 100%，A 档的「表外回落码点」问题不存在 |

##### D 档的三条实现红线（**PM 复核实测后新增，工程师必读**）

我在 Node v22.22.2 上复核发现：`Intl.Collator("zh")` 的**整串比较**行为与本文档 §4.1 的类别序**不一致**：

```
collator.compare(整串) 实测结果：
  10 | 100 | 2012 | 9 | 阿甘正传 | 宙斯之子 | Avatar | éclair | Eclair | Zeus
                        ^^^^^^^^^^^^^^^^^^^^^^ 汉字排在拉丁字母**之前**
  另有：大小写有 tertiary 差异（avatar < Avatar）；重音有差异（éclair < eclair）；空格参与比较（"阿 甘" < "阿甘"）
```

因此：

1. **禁止用 `collator.compare(titleA, titleB)` 直接比较整串。** 它的 script 顺序是「汉字 < 拉丁」，与 §4.1 规定的 `D < L < P < O` 相反，会让 P0-2 的验收样本失败。
2. **ICU 只负责一件事：产出「汉字 → 拼音秩」**（即架构设计的 `buildHanOrder()`）。类别序（数字 / 拉丁 / 汉字 / 其它）由**权重流自己控制**，不受 ICU 影响 —— 这样 §4.1 的 D<L<P<O 与 D 档才能共存。
3. **大小写、重音、标点、空白一律在归一化阶段自行处理**（`toLowerCase()` + NFD 去组合记号 + 剥离标点与空白），**不要指望 ICU**（实测 ICU 默认不忽略标点、大小写与重音均有 tertiary 差异）。

> 满足这三条后，P0-2 的验收样本 `2012 → Avatar → 阿甘正传 → 宙斯之子` 成立。**不新增 `src/utils/pinyin-data.ts`**（D 档不需要静态表）。
- 实现位置（**已决断：前端**）：新增 `src/utils/sort.ts`（纯函数，零数据表），在 `mediaStore` 内新增 `orderedItems` computed 完成「分区 → 排序」，`visibleItems()` 改为在其上做关键字过滤（见 §4.0 D7）。后端**只**承担持久化两个 KV，不承担排序计算。
  **理由**：① 列表**无分页**，全量条目已在前端内存；② 切换排序要求「立即重新排序」，前端排序零 IPC、零重查、同帧渲染；③ **不改 `get_media_list` 命令契约**（约束 B8）；④ 纯函数天然可单测；⑤ **后端路径要在 Rust 里再实现一份拼音 = 第二真源，必错**（故原 P1-3 后端路径取消，见 §10）。

### 4.2 时间键（按时间排序）——以哪个时间为准

**结论（决策 + 理由）**：

| 排序键 | 取值字段 | 粒度 | 是否有 NULL | 默认 |
|---|---|---|---|---|
| **上映 / 首播年份**（默认时间键） | `media.year`（INTEGER） | **年** | 是（刮削前 / 文件名无年份时为 NULL） | ✅ 选中此键时的默认 |
| **添加时间** | `media.added_at`（INTEGER，NOT NULL，Unix 时间戳） | 秒级 | 否 | — |

- **理由 1（为什么默认用上映 / 首播时间）**：用户说的是「按时间排序」并特别点名了「上映 / 首播时间」，影视库的直觉是按**作品自身时间**浏览（按年代、按系列上映顺序），而不是按入库时间。添加时间更多是「收纳 / 待处理」视角，故保留为第二选项。
- **理由 2（为什么只能是「年份」而不是「日期」）**：**当前 `media` 表没有 `release_date` / `first_air_date` 列**（只有 `episodes.air_date`，那是**集**级别且只有刮削过的剧集才有）。在「只做增量迁移、最小变更」约束下，**本次不新增列**，因此时间排序的上映键粒度为**年**，UI 文案必须写「上映 / 首播**年份**」，不写「上映日期」，避免用户误以为精确到日。
- **比较规则**：`year` 数值升序为正序（旧 → 新）；同年 → 按 4.1 的名称键升序 → 按 `id` 升序。`added_at` 同理（早 → 晚为正序；相同时刻 → 名称键 → `id`）。
- **缺年份 / 缺日期的条目如何归类**：见 4.3 —— 缺 `year` 属于「缺少元数据」，**进入末尾分区**（不是「在时间排序内部再排末尾」），且在分区内部因时间键不可用而**按名称键排序**。
  > 注意区分：`added_at` 恒非空，所以「添加时间」排序下**不会**有条目因时间缺失而进末尾分区，只有 `type=unknown` / `title` 为空的才会。
- **剧集怎么算**：剧集同样用 `media.year`（TMDb / TVDB 的首播年份），与电影共用同一字段，不做区分。

### 4.3 「无法被识别为电影或剧集」的可判定字段清单

**分区因子 `identified(item)`（三条硬判据，全部满足才算「已识别」）：**

| # | 判据 | 字段 / 条件 | 说明 |
|---|---|---|---|
| J1 | 类型已识别 | `item.type === "movie"` 或 `"tv"` | `unknown` 及任何非预期取值 → 未识别。**判定只读 `type` 字段值，不重新跑类型判定逻辑**（`core/mediatype.rs` 的唯一权威地位不变） |
| J2 | 有可用标题 | 4.1 的取串优先级链**至少有一个**非空（trim 后非空） | 连标题都没有 = 无法参与任何排序 |
| J3 | 有上映 / 首播年份 | `item.year !== null && item.year !== undefined` | 缺年份 = 缺排序所需的核心元数据 |

**明确「不算」缺少元数据的字段（不要自由发挥）：**

| 字段 | 是否作为判据 | 理由 |
|---|---|---|
| `tmdb_id` / `tvdb_id` | ❌ 否 | 刮削是**可选**动作。若把「没刮削」当未识别，未刮削的正常电影会被整批沉底，直接违背用户意图 |
| `poster_path` / `backdrop_path` | ❌ 否 | 缺海报是图源问题，与「是不是电影」无关 |
| `overview` / `genre` / `vote_average` | ❌ 否 | 展示增强字段，缺失不影响识别 |
| `duration` / `resolution` / `file_size` | ❌ 否 | 文件属性，非识别元数据 |
| `episode_count` | ❌ 否 | 电影本来就没有集数 |

**分区与拼接（固定顺序，与当前排序键无关）**：

```
最终顺序 = sort(已识别分区, 当前规则, 当前方向)  ++  sort(未识别分区, 当前规则, 当前方向)
```

- 分区判定**不随排序键变化**，保证切换排序方式时条目不会在「已识别 / 未识别」之间来回跳。
- 未识别分区内部「仍按当前所选规则排序」；若当前规则是时间排序而该条目缺 `year`，则其时间键不可用 → **回落到名称键**（这就是 4.2 里那句「按名称键排序」的来源）。
- **补 D6（架构补齐的空档，PM 确认）**：未识别分区**内部**，时间键缺失（缺 `year`）的条目排在该分区的**最末**（NULL 视作最大），其内部再按名称键排；与 §4.1 二级「`year` NULL 视作最大」保持同一口径。

### 4.4 正序 / 倒序的明确行为

**结论：倒序 ≠ 整体反转。未知分区恒定在末尾，倒序只在各分区内部生效。**

推理依据：用户同时说了「统一排在列表末尾」和「未识别条目内部仍按当前所选规则排序」。若整体反转，未知分区会被翻到列表最前，与「统一排在末尾」直接矛盾。因此：

| 行为 | 定义 |
|---|---|
| 分区顺序 | **恒为「已识别 → 未识别」**，方向切换不影响分区先后 |
| 已识别分区内部 | 按当前规则排序后，根据方向决定是否取反 |
| 未识别分区内部 | 同样按当前规则排序后，根据方向决定是否取反 |
| 方向语义 | 名称：正序 A→Z / 倒序 Z→A；上映年份：正序 旧→新 / 倒序 新→旧；添加时间：正序 早→晚 / 倒序 晚→早 |

**补 D4 / D5（架构补齐的空档，PM 确认）**：

- **D4：倒序只取反「主键」，兜底链（名称键 → `year` → `id`）恒升序。** 兜底链的作用是「消除歧义」而非「参与用户感知的方向」；恒升序让「同年同名的几条」在正序 / 倒序下相对顺序一致，用户可预测。
- **D5：倒序禁止用 `Array.reverse()`。** `reverse` 会把主键相等的一批也翻转，破坏兜底链语义；必须实现为 `cmp(b, a)`。

### 4.5 默认状态（保证「升级后首屏不跳变」）

- 默认 `sortBy = "name"`，`sortDir = "asc"`。
  → 与后端现有的 `ORDER BY m.title COLLATE NOCASE ASC, m.year ASC` 方向一致，老用户升级后首屏顺序**基本不变**（仅中文条目的相对顺序因拼音规则而变），符合「最小变更」。

## 6. UI 设计稿（文本描述）

**位置**：`src/App.vue` 的 `.stickytop > header.topbar` 内，紧跟在**标签下拉 `.tagselect` 之后、「＋新建资源」按钮之前**。

> 现有顺序：`h1` → 搜索框 → 标签下拉 → ＋新建资源 → 📂导入文件夹 → ↩撤销(tree) → ☑选择 → 🔍重新识别 → 扫描媒体库 → 批量刮削 → 停止扫描 / 停止刮削。
> 排序是**展示类**控件，与「搜索 / 标签」这两个筛选控件相邻成组；放在此处可明确与右侧那排**操作类**按钮（新建 / 导入 / 扫描 / 刮削）区分开，用户不会把「排序」误当成「扫描」一类的动作。

**形态**（复用现有样式，不新增 CSS 变量）：

```
[ 排序  名称（拼音 A→Z） ▾ ]  [ ↕ 正序 ]
```

1. **排序方式**：原生 `<select class="tagselect">`（**直接复用标签下拉的 `.tagselect` class**，字体、边框、圆角、hover 自动与现有工具栏一致，零样式改动）。
   - `value="name"` → 显示 `名称（拼音 A→Z）`，`title="按片名拼音排序；数字在最前，其次英文，再次中文"`
   - `value="year"` → 显示 `上映 / 首播年份`，`title="以条目的上映 / 首播年份为准（库内只存到年份粒度）；没有年份的排在末尾"`
   - `value="added"` → 显示 `添加时间`，`title="以条目入库（添加）时间为准"`
2. **方向**：一个 `.btn .btn-ghost` 按钮，放在 select 右侧。
   - 正态显示 `↑ 正序`，点击后变 `↓ 倒序`，再点回来；`title="切换正序 / 倒序（未识别的条目始终排在末尾）"`。
   - 用**按钮而非第二个下拉**：方向只有两个取值，一点即切，比下拉少一次操作。
3. **不打架的三条硬规则**：
   - **不加快捷键角标**（不生成 `<span class="sc">{{ fmt(...) }}</span>`），也不注册新的全局快捷键 —— 现有 `shortcutSelectAll / Invert / Confirm / Clear` 的键位一律不动。
   - **不新增图标字体 / 第三方组件库**；`↑ ↓ ↕` 用现有文本字符即可。
   - **显隐条件与搜索框一致**：`v-if="!inSettings && !inTree"`（设置页与剧集树视图隐藏）。
4. **不改的东西**：`.stickytop` 的 sticky 行为、多选工具条（`.selbar`）的出现逻辑、卡片渲染、滚动位置策略 —— 全部保持原样。

## 7. 持久化决策

**决策：记住，且复用现有机制。**

| 项 | 方案 |
|---|---|
| 存哪 | 后端 `settings` 表（key/value），新增两个 key：`sortBy`（`"name"` / `"year"` / `"added"`）、`sortDir`（`"asc"` / `"desc"`） |
| 前端 | `settingsStore` 新增两个 ref，走现有 `getSettings` / `setSettings`；`Settings` 结构体加两个带 `#[serde(default)]` 的字段（向后兼容，旧库读不到就回落默认） |
| 是否需要 schema 迁移 | **不需要**。`settings` 是 KV 表，新增 key 即生效，符合「只做增量迁移」 |
| 默认值 | `sortBy = "name"`、`sortDir = "asc"`（与后端现有默认 ORDER BY 一致，升级不跳变） |
| 何时写库 | 用户切换时立即落库（与现有设置项写入时机一致），不需要「保存」按钮 |
| 不做 | 不引入 `localStorage`（项目目前全量走 SQLite，混两套持久化会造成状态不一致） |

## 10. 不做的事（防止范围蔓延）

- 不新增数据库列 / 表，不做数据迁移。
- **不新增 `src/utils/pinyin-data.ts` 之类的静态拼音表**（D 档不需要；也禁止联网抓取数据生成 —— 违反 C11 / B2）。

- 不改类型判定逻辑（`core/mediatype.rs` 一字不动）。
- 不引入分组头（A/B/C 索引条）、不引入虚拟滚动、不做分页。
- 不改海报卡片、详情弹窗、侧边栏的任何视觉与交互。
- 不注册新的全局快捷键。
- 不写任何媒体文件。
