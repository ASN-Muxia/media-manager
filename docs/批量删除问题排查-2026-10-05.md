## 一、先说结论

**后端没有「部分删除 / 重复删除 / 误删相邻数据」这类问题** —— 删除是单事务、
`ON DELETE CASCADE` 真的生效、重复 id 只删一次、重复调用幂等（实测确认，见下）。

真正的问题有两类：

1. **前端选中集合的生命周期没人管** —— 会删到看不见的条目、删完留脏 id、提示数字对不上；
2. **健壮性缺口** —— 删不到时报成功（静默失败）、删除跑在主线程、层级有环时会造出自环。

## 二、实测确认「是好的」的部分（避免以后误改）

| 项 | 结论 | 依据 |
|---|---|---|
| 关联数据清理 | **干净**：单集 / 标签关联 / 分类关联 / 观看状态全部级联删除 | `delete_media_cascades_to_every_related_table` |
| 级联开关 | 依赖 `PRAGMA foreign_keys = ON`，`migrate()` 末尾**无条件开启**，别删 | 同上用例盯住 |
| 重复 id | 传三遍只删一行，返回 1 | `delete_normalizes_duplicate_and_invalid_ids` |
| 幂等 | 同一批删第二次返回 0，**不报错** | `delete_is_idempotent` |
| 部分 id 已不存在 | 返回真实条数（如请求 3 条只存在 1 条 → 返回 1） | `delete_reports_real_count_when_some_ids_are_gone` |
| 父子同删 | 孙辈上提到顶层，不留孤儿 | `delete_parent_and_child_together_promotes_grandchild` |
| 批量规模 | SQL 变量上限实测 **32766**（不是老资料里的 999），1200 条一次删没问题 | 已实测 |

事务保证：删除整批在**一个事务**里，中途出错整体回滚，不会出现「删了一半」。

## 三、修掉的六个问题

### P0-1【误删】改关键字后，「删除所选」会删掉看不见的条目

- **现象**：用户多选 10 条 → 输入关键字过滤到只剩 2 条 → 点「删除所选」→ **10 条全被删**，
  其中 8 条不在当前视图里，用户根本没看见。
- **根因**：`App.vue` 里 `keyword` 是 `v-model` 直接绑 store，**没有任何裁剪**；
  而 `setView`（切换栏目）是会 `selected.value = []` 的。两条路径不一致。
  确认框读的是 `media.selected.length`，所以连提示都是错的。
- **修法**：新增 `pruneSelection()`（只保留当前可见的选中项）+ `watch(keyword, ...)` 触发。
  换栏目仍是整体清空，改关键字只剔掉被过滤掉的那部分 —— 既不误删，也不至于打一个字就清空多选。

### P0-2【静默失败】单条删除删不到时报成功

- **根因**：`delete_media` 返回 `Result<(), String>`，`delete_nodes_sync` 对不存在的 id
  返回 `Ok(0)`，前端无条件 `note("已从媒体库移除")`。
- **修法**：删除 0 条时**明确报错**（`找不到 id 为 N 的资源，可能已经被删除了`）。
  重复删除同一个 id 天然走这条路径，所以「幂等」表现为第二次报错，而不是谎报成功。

### P0-3【脏状态】单条删除后 id 仍留在选中集合

- **根因**：`remove()` 只做 `closeDetail() + load()`，没动 `selected`。
- **后果**：下一次「删除所选」带着已删 id 再跑一趟，返回条数与用户看到的勾选数对不上。
- **修法**：新增 `dropFromSelection()`，`remove()` 与 `removeByIds()` 都调；
  且剔除的是**请求过的全部 id**（含本来就不存在的），不是只剔成功删掉的。

### P1-1【反馈不准】实际条数少于请求数时不解释

- **修法**：`已删除 2 条资源，另有 1 条已不在库中`。
  后端是单事务，条数变少只可能是「有些 id 不在库里」，说清楚用户才不会再点一次。

### P1-2【误清空】树视图删除顺手清掉海报墙的勾选

- **根因**：`App.vue onTreeDelete` 先 `media.setSelected(ids)` **覆盖**选中集合，
  再 `removeSelected()`（内部 `clearSelection`）。
- **修法**：新增 `removeByIds(ids)` 作为**唯一真正的删除入口**，树视图直接按 id 删，
  只剔除这一批，不动用户其他勾选。`removeSelected()` 退化成「取选中集合 + 转提示」。

### P1-3【UI 阻塞】删除命令是同步的

- 三个删除命令原本都是 `pub fn` 同步命令，跑在 Tauri 主线程上，批量删会锁住界面，
  违反项目既有约定（IO 必须 `async` + `spawn_blocking`）。
- **修法**：改成 `async` + `spawn_blocking` + **自己开一条连接**（与 `import_folder` 同款，
  WAL 下安全）。对前端零改动：`invoke` 的参数与返回类型都没变。

## 四、最难的一处：环会造出「自己挂自己」

`delete_nodes_sync` 要把被删节点的子级**过继给祖父**。原实现边走边判：
遇到「第一个不在删除名单里的祖先」就停。

`parent_id` **没有外键约束**，存量库里理论上可能存在环（A 挂 B、B 又挂 A）。
那种情况下，「第一个不在名单里的祖先」恰好是**它自己的子节点** —— 把子级挂上去
就变成 B 挂 B，比孤儿更难查。

> 我第一版修复只在「循环检测到重复」时兜住，测试立刻抓出来了：
> `B.parent` 变成 `Some(2)`（B 自己）。

**正确做法**：先**整条走到根**（用 `seen_up` 检测是否成环），
再在收集到的祖先链里 `find` 第一个不在删除名单里的；**撞环一律挂顶层 `None`**。
层级上限 `MAX_DEPTH = 4`，多走几步没有成本。

另外入参统一走 `normalize_ids()`：**去重 + 丢弃 `id <= 0`**，保序。
`delete_rows`（删单集）同样适用。

## 七、真正让「清空 / 批量删除」失败的两个根因

第一版排查全绿但用户仍然失败。**教训：运行时问题先读日志，别上来就读代码。**

### 诊断路径（可复用）

1. **读前端错误日志** `%APPDATA%\com.example.media-manager\frontend_error.log`
   只有一类错误：`unhandledrejection: dialog.confirm not allowed. Command not found`。
   全文 grep 没有**任何**后端 SQL 报错 → 删除命令的错误被 store 的 try/catch 吞成 toast 了。
2. **查真实库状态**：`media` 仍是 77 条 → 删除确实没执行。
3. **在库副本上复现**：`DELETE FROM media` → `database disk image is malformed`。

### 根因 ①：`media_fts` 检索索引损坏（这是「失败」的直接原因）

删 media 时 `media_fts_ad` 触发器要从 FTS 索引里删行，索引一碰就
`database disk image is malformed` → 清空媒体库和批量删除**一起**失败。
而 `SELECT` 完全不受影响，所以列表照常显示，看上去就像代码坏了。

**最坑的是查不出来**：

| 检查手段 | 结果 |
|---|---|
| `PRAGMA integrity_check` | **ok** |
| `INSERT INTO media_fts(media_fts) VALUES('integrity-check')` | **通过** |
| 真的 `DELETE FROM media` | **malformed** ← 只有这一步暴露 |

只有真的去做一次删除才会暴露，所以静态检查永远发现不了。

**修法**：`INSERT INTO media_fts(media_fts) VALUES('rebuild')` 重建索引（**只动索引，
不碰 `media` 表任何一行**）。在真实损坏库上实测：

```
DELETE FROM media                -> database disk image is malformed
INSERT INTO media_fts ... rebuild -> OK
DELETE FROM media                -> OK
```

代码里做成**自愈**：`delete_nodes_sync` 与 `clear_library` 遇到 malformed 就
重建索引并重试一次；重建本身失败则抛原始错误，不掩盖真因。

⚠️ **真实库那种内部不一致在测试环境构造不出来**（依赖 SQLite 版本行为：
3.53 上 `DELETE FROM media_fts_idx` 能凑出同样症状，rusqlite 编的这个版本打不坏）。
所以用例写成「复现了就要求自愈成功、没复现就保证正常删除不受影响」，
判定逻辑 `heal_fts_if_malformed` 另用独立用例钉住 ——
**不写一条永远在走 else 分支的假测试**。

### 根因 ②：`window.confirm` 被 dialog 插件覆盖坏了（独立隐患）

`tauri-plugin-dialog` 2.7.3 注入的 `init-iife.js`：

```js
window.confirm = async function(i) {
  return await n("plugin:dialog|confirm", { message: i.toString() })
}
```

但插件 2.x 已把 confirm/ask 并进 `message`，`dialog:default`
（= `allow-message` / `allow-save` / `allow-open`）里**没有** confirm 命令
→ 每次调用都 reject → 就是日志里那条 `dialog.confirm not allowed`。

**更危险的副作用**：覆盖后 `window.confirm` 是 **async**，返回 Promise。
而所有调用点都是同步写法：

```ts
const ok = window.confirm("确定删除？");
if (!ok) return;          // !Promise 恒为 false → 这行永远不成立
await removeSelected();   // 于是直接删了，连问都不问
```

**二次确认被整个绕过**。这意味着只修根因 ① 的话，删除会退化成
「点一下就直接删、不弹确认」—— 所以两个必须一起修。

**修法**：新增 `src/utils/confirm.ts` 的 `askConfirm()`，走插件的 `confirm()`
（它用的是**已授权**的 `plugin:dialog|message`），并要求调用点 `await`；
拿不到明确答复一律按「取消」处理 —— 宁可让用户删不掉，也不能绕过确认直接删。
替换了 6 处 `window.confirm`（App.vue ×3、MediaDetail、SettingsPanel、Sidebar）。
