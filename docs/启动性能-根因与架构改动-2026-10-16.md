# 启动性能：根因与架构改动（2026-10-16 · 第 15 轮）

用户报告：「现在软件启动非常慢，更改一下架构使启动速度加快」。用户批准两个方案都做。

验证：tsc 0 错；vitest **28 文件 / 513 用例**；cargo test **552 / 0**；cargo check 警告 0；
分层合规通过；vite build 成功；打包冒烟通过。

---

## 一、根因（实测，不是猜）

### 主因：启动器会**静默**跑一次 41.6 秒的完整重建

`scripts/启动影视库.vbs` 原来这样判定：

    newestDist = dist 目录下所有文件的最新 mtime
    If exe.mtime >= newestDist Then 直接启动 Else 隐藏窗口跑一次 start.bat

而 `start.bat` 的构建判据（`mjs/dev/need-build.mjs`）把 **`dist` 当作 Rust 重编的输入** ——
因为前端产物原本是**编译期嵌进 exe** 的。于是：

**只要 `dist` 比 exe 新，就会用隐藏窗口重编 Rust 并重新链接 17MB exe。**

实测这个重编：**41.6 秒**（`cargo build --release`，只改前端、其余不变）。
更糟的是窗口是**隐藏**的 —— 用户看到的是「双击之后卡死半分钟」，没有任何提示。
而 `dist` 比 exe 新恰恰是**开发中的常态**（每跑一次 `vite build` 都会发生）。

### 排除掉的两个嫌疑（都实测过）
- **WebView 缓存清理**：`boot::prepare` 每次启动清理 GPU/着色器缓存 —— 实测只用 **4~7 ms**，不是瓶颈。
- **启动器脚本本身**：`start.bat --no-build` 端到端 **114 ms**；exe 启动到前端就绪 **300~1063 ms**。都很快。

### 顺带发现的两个放大因素
1. `need-build.mjs` 的 rust 判定把**整个 `dist` 目录**列为输入 —— 任何前端改动都逼着重编 41 秒。
2. **残留实例占住 exe** 会让链接失败或变慢（实测报「拒绝访问」os error 5）。

## 二、方案 1：启动器体验与判据（小改动）

### 1) `mjs/dev/need-build.mjs` —— rust 判定不再吃 `dist`

删掉输入列表里的 `"dist"`，并写明理由。现在：
- 改前端（`src/**`）→ 只要求 `vite build`（亚秒），**不再要求 cargo build**；
- 改 `src-tauri/src` / `Cargo.toml` / `build.rs` / `tauri.conf.json` / `capabilities` → 仍要求重链。

实测：

    dist/index.html 已 touch（比 exe 新）
    need-build --rust --profile release  → exit=1（跳过构建）OK
    need-build --frontend                → exit=1 OK
    touch src-tauri/src/lib.rs 后 --rust → exit=0（需要构建）OK
    dist 缺失时 --frontend               → exit=0（需要构建）OK  ← 安全兜底

### 2) `scripts/启动影视库.vbs` —— 去掉 dist-mtime 触发、显示进度、清残留

改动（**保持 GBK + CRLF 字节级兼容**，`cscript` 解析中文注释才不会坏）：
- **删掉**「比较 dist mtime 就重建」那整段（含已无人调用的 `NewestUnder`/`newestDist`）；
- 改用与 `start.bat` **同一份判据**：新增 `NeedBuild(args)` 去调 `need-build.mjs`，
  退出码 0 = 需要构建（避免两处规则各写一套、迟早不一致）；
- 构建窗口从 `0`（隐藏）改成 **`1`（正常窗口）** —— 用户能**看见**进度，不再像卡死；
- 构建/启动前调用新增的 `KillStale()`：`taskkill /F /IM media-manager.exe`，
  解决「残留实例占住 exe 导致链接失败」与「多实例抢 WebView2 目录误触发看门狗」；
- `Option Explicit` 下补上 `needFe` / `needRs` 声明（否则运行时报「变量未定义」）。

**验证方式**（绝不用真跑启动来试）：把 VBS 复制一份、两个 `shell.Run` 换成回显，用 `cscript` 跑：

    快路径分支：>>> 快路径：直接启动 exe（不构建）      ← dist 比 exe 新时的实际情况
    构建分支  ：>>> 清理残留实例 / >>> 构建路径：needFe=True needRs=True

并做了变量审计：`Option Explicit` 下所有被赋值的标识符都已声明（结果为空）。

## 三、方案 2：运行时读 dist + 嵌入回退（架构改动）

### 思路
编译期嵌入前端是「改前端要重链 41 秒」的**结构性**原因。改成**运行时优先读磁盘 `dist`**，
嵌入的那份退化为兜底：

| 场景 | 行为 |
| --- | --- |
| 开发机（dist 存在） | 读磁盘 → vite build 后重开即生效，**不需要 cargo build** |
| 分发机（没有 dist） | 编译期记下的绝对路径不存在 → **回退嵌入**，行为与改动前完全一致 |
| dist 被删 | 同上，自动回退，不会白屏 |

### 实现（新增 `src-tauri/src/assets.rs`）

- 实现 `tauri::Assets` trait；接线用 **`Context::set_assets`**（官方对象替换接口，
  **会把旧值还回来** —— 正好就是 `generate_context!` 那份嵌入资源，一步拿到手当兜底）。
- dist 路径由 `build.rs` 用 **`cargo:rustc-env=MM_DIST_DIR=<绝对路径>`** 在编译期写死。
  刻意不用「相对 exe 推 ../..」：exe 在 `target/<profile>/` 下，层级随构建方式变化，
  打包后必然算错。而绝对路径在开发机存在、在别人机器上不存在 —— 后者正好触发回退。
- `iter()` / `csp_hashes()` 直接委托嵌入那份：本项目 csp 是 null，自己重算只会引入
  「算错 → CSP 变严 → 页面崩」的风险。

### 路径穿越防护（这是本地文件服务器，必须做）

`safe_relative()` 白名单式拼接，`AssetKey` 里出现以下一律拒绝、直接回退嵌入：
- `..`（唯一能把结果送出 dist 之外的东西）；
- `\`（Windows 上同样是分隔符）；
- `:`（能写出盘符 `C:`，也能写出 NTFS 备用数据流 `index.html:stream`）。

拒绝 `..` 之后 `root.join(rel)` 不可能越界，因此不必再 `canonicalize`
（那要求路径已存在，会给「读不到就回退」的正常分支添麻烦）。4 条单测覆盖。

### `build.rs`
删除 `println!("cargo:rerun-if-changed=../dist")` 并重写注释说明为什么现在不该再监控。

## 四、端到端验证（两条路都实测）

### (a) 改前端 → 不重编 → 应用真的读到磁盘新内容 [通过]

前两次探针**都无效**，记下来免得再踩：
1. `<script type="module">import 不存在的文件` → **资源加载错误不冒泡到 `window.onerror`**，
   所以「日志没报错」既可能是读了嵌入、也可能探针根本没信号；
2. 内联 `<script>throw</script>` → **经典内联脚本在解析期就执行，早于 deferred module**
   （`main.ts` 注册 `onerror` 那一刻还没到），抛了也没人上报。

有效探针 = **内联 `type="module"` 的 throw**（deferred，按文档顺序在 `main.ts` 之后执行）：

    注入：dist/index.html 尾部 + <script type="module">throw new Error("PROBE_RUNTIME_DIST_OK_7731")</script>
    启动：直接跑**已有的** exe，不跑 cargo build
    日志：error: Uncaught Error: PROBE_RUNTIME_DIST_OK_7731 @ http://tauri.localhost/:12:31
    exe mtime：1792160506 → 1792160506（**未变**，证明没重编）

### (b) dist 缺失 → 回退嵌入 [通过]

    mv dist dist.hidden → 启动（不重编）→ frontend_error.log 出现 boot / mounted / frontend_ready ok，无 error
    → 回退生效；随后恢复 dist（index.html 回到 395 字节、无探针残留）

### (c) 完整「双击」判定路径 [通过]

    dist/index.html 22:25:14  >  exe 22:21:46   ← 正是以前会触发 41s 重建的状态
    跑真实判定（副本回显）→ >>> 快路径：直接启动 exe（不构建）

## 六、遗留 / 注意事项

1. 🔴 **绝对不能并发启动多个实例**。WebView2 数据目录是独占的，多实例互抢会让看门狗判定「白屏」→
   弹「影视库启动异常」→ 重置 WebView 缓存。**本次排查中我自己就踩了**：为量启动耗时反复启动、
   上一轮没退干净就启下一个，真的把用户那个错误弹窗触发出来了。测启动必须：
   `taskkill` 确认 0 实例 → 启一个 → 测完 `taskkill` → 再下一个。
2. 启动器已内置 `KillStale()` 兜这件事，但它只在「需要构建」时调用；**开发/测试时自己也要守纪律**。
3. `dist` 被 `mjs/build/package.mjs` 排除在分发包外（`git ls-files` 模式）—— 这与本次架构**正好配套**：
   分发包不带 dist，运行时必走嵌入回退。**前提是发布前必须跑过一次 `cargo build`**，
   否则 exe 里嵌的是旧前端。
4. `MM_DIST_DIR` 是**编译期绝对路径**。同一份 exe 换机器后该路径不存在 → 回退嵌入（符合预期）。
5. 本轮仍未 `git add`、未重新打包分发。

# 更正：删除 `rerun-if-changed=../dist` **并不能**免除重编（同日 22:45）

## 更正什么

本文档第三节「build.rs」与第五节曾表述为「删掉那行就不再触发重编」。
**这个说法不准确**，经实测更正如下。

### 实测证据（决定性）

    cargo build --release  基线（无任何改动）      → Finished in 0.25s   (341 ms)
    touch dist/index.html（只改 mtime、内容不变）→ Compiling media-manager ... 32.50s (32581 ms)

## 真正的机制

`tauri::generate_context!` 宏会为**每一个资源**发射一行 `include_bytes!`
（`tauri-codegen-2.6.3/src/embedded_assets.rs:399-403`）：

    // add original asset as a compiler dependency, rely on dead code elimination to clean it up
    assets.append_all(quote!(#key => {
        const _: &[u8] = include_bytes!(#input);   // <== 关键：把 dist 原路径变成 rustc 依赖
        include_bytes!(#output)
    },));

于是 `dist` 下的文件被写进 `target/release/deps/media_manager_lib.d` 与 `media-manager.d`，
**由 rustc 的依赖追踪（不是 Cargo 的 build-script rerun）决定要不要重编**。
实测确认：build script 的 `invoked.timestamp` 停在 22:21:01 不再更新（说明 `rerun-if-changed` 的删除**生效了**），
但 `Compiling media-manager` 依然发生 —— 重编是宏造成的，**与 build.rs 那条监控无关**。

## 影响（说清边界，别夸大也别缩小）

| 路径 | 是否受影响 |
| --- | --- |
| **用户双击 `启动影视库.vbs`** | ✅ **不受影响**。启动器走 `need-build.mjs --rust`，其输入列表**已不含 `dist`** → 判定「跳过 cargo」→ 实测 **1 秒**可启动 |
| 手工 `cargo build --release` / IDE 构建 / CI | ⚠️ **仍会重链 32~37 秒**（因为改过前端 → dist 里文件比产物新） |

**结论**：用户报的「启动非常慢」在**正常使用路径上已解决**；残留的只是**开发者手工构建**时的耗时。

## 为什么没有采用「占位 frontendDist」方案

有人提出把 `frontendDist` 指向一个固定占位目录（让宏去追踪那个目录，`dist` 怎么变都不再触发重编）。
**评估后不采用**，因为它引入**用户可见的回归风险**：

- `MM_DIST_DIR` 是**编译期烧死的绝对路径**（已验证 exe 内含 `G:\AI agent\media-manager\dist`）；
- 该路径在以下情况会失效：**项目被改名 / 移动**、exe 被拷到别的盘或机器；
- 一旦失效 → 运行时回退到**嵌入资源** → 若嵌入的是占位页，**用户看到的是占位页而不是软件**。

用一个「开发者手工构建慢 32 秒」换一个「移动文件夹后界面变成占位页」是不划算的。
因此**保留 `frontendDist: "../dist"`**，让嵌入回退里始终是**真实前端**。

## 若将来要彻底消除（可选，需另做设计）

可以「占位 `frontendDist` + 运行时按**多候选路径**解析」：
1. `MM_DIST_DIR`（编译期绝对路径）；
2. exe 相对路径推 `../../../dist`（项目移动后 dist 跟着走，仍然命中）；
3. 最后才回退嵌入。
这样即使项目改名/移动也不会显示占位页，同时彻底断开 rustc 对 `dist` 的依赖。
代价是运行时路径解析变复杂、并需要一个 `dist-embed` 占位目录；
**本轮未做**，等有明确需要再评估。
