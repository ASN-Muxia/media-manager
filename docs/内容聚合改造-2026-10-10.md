# 内容聚合改造（2026-10-10）

本轮目标：把「聚合」这件事收敛成**一套机制、两个入口**，并修掉拖拽聚合做不成的老问题。

## 一、改了什么

### 1. 修复「拖动聚合无法完成」

**根因（交互层，不是后端）**：`PosterGrid.vue` 的 `armDrag()` 在每次 `pointerdown` 时按条件改写
`.cell` 的 `draggable`：

```ts
const want = ev.pointerType !== "touch" && (onGrip || ev.altKey || ev.ctrlKey || ev.metaKey);
cell.draggable = want;
```

默认状态下 `.cell` **根本不可拖**。用户最直觉的「按住海报拖到另一张海报上」被设成 `false`，
然后被滑动框选接走 → 表现为「拖不动 / 聚合失败」。唯一能走通的两条路都藏在暗处：
从 `⠿` 把手起拖（把手 `display:none`，`:hover` 才出现），或按住 Alt/Ctrl。

第二个问题：`onDragStart()` 里批量还要求 `props.selectable`，于是「多条目聚合」= 先进「选择」
模式勾选 → 再配合 Alt 或把手拖，两步隐藏操作叠在一起，等于不可用。

**后端本来就是对的**（已逐行核过，未改动）：
`commands/tree.rs::move_nodes_sync`（单事务 + 同级重排 + `validate_drop`）、
`load_edges`（`SELECT id, parent_id FROM media`，**不按类型过滤**）、
`utils/tree.ts::canDrop`、`mediaStore.moveNodes`、`App.vue::onGridMove`（带 `await media.load()` 回刷）。

**修法**：加显式的「聚合模式」开关。

| 位置 | 改动 |
| --- | --- |
| `src/components/PosterGrid.vue` | 新增 `grouping?: boolean` prop；`armDrag` 的 `want` 加 `props.grouping \|\|`；复位值改成 `!!props.grouping`（不再写死 `true`）；`onGridPointerDown` 在聚合模式下调完 `armDrag` 就 return，不让滑动多选接管 pointer 流；`onDragStart` 的批量条件去掉 `props.selectable`；`.grid.grouping .grip { display: flex }` 让把手常显 |
| `src/stores/mediaStore.ts` | 新增 `grouping` ref 并加进 `return {}`（setup store 漏 return 会静默读到 `undefined`） |
| `src/App.vue` | 顶栏「🔗 聚合」按钮 + `enterGrouping()`；聚合模式提示条（复用 `.selbar`）；`<PosterGrid>` 传 `:grouping` 且 `:selectable="media.selecting \|\| media.grouping"` |

**为什么必须走开关**：原生 HTML5 拖拽一旦启动，浏览器会**掐断 pointer 事件流**（补发 `pointercancel`），
滑动框选当场失灵。「卡片随时可拖」与「按住划过框选」在鼠标下是互斥的，所以只能二选一，
而不能靠"拖多远算拖"这种阈值去猜。

**触摸是例外**：HTML5 拖拽在触摸下压根起不来（浏览器层面，绕不过去）。若聚合模式下也无条件
扣住 `pointerdown`，触摸用户会拿到一个既不能拖、又不能长按多选的死网格，
所以条件是 `props.grouping && ev.pointerType !== "touch"`。

**进入/退出都清空勾选**：批量只看 `selected`，残留勾选 + 拖一张 = 搬走十几张的惊吓。

### 2. 删除剧集层级栏目

- 删除 `src/components/SeriesTree.vue` 与其 spec；
- `App.vue` 移除 `VIEW_TREE` / `inTree` / `tree` / `treeLoading` / `loadTree` / `copyNode` 及 5 个
  `@onTree*` 处理函数；视图链收敛成 `MediaDetail(v-if) → SettingsPanel(v-else-if) → PosterGrid(v-else)`；
- **保留**全部 `parent_id` 数据与后端树命令（`move_media_nodes` / `undo_tree_op`）——撤掉的是入口，不是能力；
- `src/api/commands.ts` 清掉两个已无调用方的前端包装 `getMediaTree()` / `copyMediaNode()`
  （它们是树视图专属入口）；`MediaTreeNode` / `TreeOpResult` / `TREE_MAX_DEPTH` / `moveMediaNodes` /
  `undoTreeOp` 仍在用，保留。后端 `get_media_tree` / `copy_media_node` 仍注册且有单测覆盖，
  属通用数据与撤销能力，不带 UI 入口，不构成"残留入口"。

### 3. 聚合调整迁进详情页（`MediaDetail.vue`）

新增「聚合成员」区（`members` / `isGroup` / `groupSelfId` / `moveMember` / `runTreeOp` / `reloadDetail`）：

- 成员行：序号 / 海报 / 标题（点击打开该成员详情）/ ↑ / ↓ / ✎ / 移出；
- ↑↓ = `moveNodes([id], self, i±1)`——**同级内下标**，与后端 `move_nodes_sync` 的
  「siblings 排除被搬者后再插到 `at`」语义对齐；
- ✎ 复用已有 `emit("edit", m)` 入口，不新造弹窗；
- ＋ 加入聚合：候选用 `subtreeOf(自己)` 排除自己与全部后代（防成环），再加一道 `id === self` 兜底；
- ↶ 撤销走 `store.undoTree()`（`undoDepth` 为 0 时置灰）；
- 「取消聚合」：走确认 → 全部成员一次 `moveNodes(ids, null, null)`（后端单事务）；
- 变更统一走 `runTreeOp`：`groupBusy` 连点保护 → 成功后 `store.load()` + `store.openDetail(id)`。

### 4. 电影与剧集一致

全链路**没有任何 `type` 分支**：

- 后端 `load_edges` 不按类型过滤；
- 前端 `isGroup` 判据只有 `child_count > 0 || members.length > 0`；
- 文案统一用「条目 / 成员 / 聚合」。

## 二、边界情况

| 场景 | 处理 |
| --- | --- |
| 已存在的老层级数据 | `parent_id` / `child_count` 原样读、原样显示，不清空不归一化；`isGroup` 取「或」，老数据只有一边为真也能显示 |
| 空聚合（`child_count>0` 但取不到成员） | 详情页走空态 + 「刷新」。原因通常是成员被删、或不在当前筛选范围内。工具条同时显示「记录到 N 个，当前能看到 M 个」。**空态下「取消聚合」照样显示**（条件已改为 `childCount > 0` 为真即可），换栏目只是可选项而非唯一出路 |
| 取消聚合 | 走确认；确认文案里的 N 是**全量子级数**（用无筛选的 `getMediaList` 现取，见第四节），有筛选外成员时额外注明。取全量失败则**不发任何 moveNodes** 并把原因写进聚合区。真正的空（`child_count === 0`）不显示按钮 |
| 成员变更后的刷新 | `moveNodes` 只改层级关系、不重拉列表，所以统一 `runTreeOp` → `load()` + `openDetail()`，否则详情页的 `child_count` 与成员列表是陈旧的 |
| 成员不在当前筛选内 | 详情页成员列表用筛选后的 `orderedItems`，看不到就是空态，UI 说明「成员可能已被删除，也可能不在当前筛选范围内」，并给出「刷新 / 换栏目 / 直接取消聚合」三条去路 |
| 排序序号 | 后端 `ITEM_COLUMNS` 已带 `COALESCE(m.sort_order,0) AS sort_order`，`MediaItem.sort_order` 一路送到前端；成员列表与封面墙建树都按 `(sort_order, id)` 排，与 `move_nodes_sync` 的 `siblings.sort_by_key` 同一把尺子。**不再用「列表先后」当同级次序**（那是展示排序偏好算出来的） |
| 层级深度 | 前端不再自己数深度（父节点被筛选掉时会偏小、进而放行后端必拒的放置）；`MediaItem.depth` 由后端 `attach_depth()` 用全表边表 + `core::tree::depth_of` 算好，前端只在缺失时退回自数兜底 |

## 四、复核轮（同日）修掉的缺陷

第一轮的 `verify.bat` 全绿只证明"改动的部分没坏",并不证明交互链路对。复核时用
「读源码 + jsdom 探针 + 桌面端真机操作」逐条重走了一遍聚合链路，找到并修掉下面这些：

### 1. 静态 `draggable` 把「静止态」语义顶掉了（`PosterGrid.vue`）

模板里 `.cell` 写死 `draggable="true"`、`.grip` 也写死一份。`armDrag()` 只在 `pointerdown`
时改写它，于是**挂载后、没按过任何一次时整墙都是可拖的**；而静态属性在 vnode 里前后恒等，
Vue 的幂等 patch 之后再也不会改写它。修法：新增 `idleDraggable = computed(() => !!props.grouping)`
当**唯一真相来源**（模板绑定 + `armDrag` 复位都读它），`.grip` 不再自己声明 `draggable`
（把手只是 `armDrag` 里 `onGrip` 的判定目标，拖拽源永远只有 `.cell` 一个）。

### 2. 「选择」与「聚合」两个模式会同时开着（`App.vue`）

`enterGrouping()` 只清勾选、没关 `selecting`，于是 `.stickytop` 里叠出**两条 `.selbar`**，
退出聚合后还莫名其妙停在多选模式。修法：`enterSelecting()` / `enterGrouping()` / `exitGrouping()`
三处互相收口，两模式互斥；`onSelectMany` 在聚合模式下也不再顺手切进多选。

### 3. 成员 ↑ / ↓ 点了没反应（`sort_order` 没贯通）

`members` 用 `orderedItems`（**展示排序**，默认按拼音名）当同级次序，把显示下标当 `index`
传给后端；后端按库内 `sort_order` 解释这个 `index`。两个序不是一回事 → 点「下移」时后端算出
的新序和旧的完全一样（`before.is_empty()` → 回「已经在…这个位置，没有改动」），而列表又按名字
重排，用户看到的就是"点了没反应"、甚至插到错位。根因是 `MediaItem` / `ITEM_COLUMNS`
**根本没有 `sort_order`**。修法：`ITEM_COLUMNS` 末尾追加 `COALESCE(m.sort_order,0) AS sort_order`
（`map_item` 同步、新列只能追加，避免旧下标错位），`MediaListItem.sort_order` 是 **snake_case**
（该结构体没有 `rename_all = "camelCase"`，只有 `media_type` 上 `rename = "type"`）；
`MediaDetail.members` 与 `PosterGrid.nodes` 都改按 `(sort_order, id)` 排。

### 4. 前端放行判定用了偏小的深度

`PosterGrid.vue::depthOf()` 沿 `parent_id` 上溯时以 `byId.has(cur)` 为界，而 `byId` 只是**当前筛选**到的
`props.items`：父节点被筛掉就当成走到了根，深度偏小，`canDrop` 于是放行后端必拒的放置
（界面画"可放置"、真的发了 `moveNodes`，后端回「层级最多 4 层」）。修法：`ITEM_COLUMNS` 末尾
加第 22 列占位 `0 AS depth`，由 `attach_depth()`（`load_edges` 全表边表 + `core::tree::depth_of`）
覆盖成真实层级，`get_media_list` / `get_media_detail` 都接上；前端 `depth: it.depth ?? depthOf(it)`
只在缺失时退回自数。

### 5. 「取消聚合」只搬看得见的成员

`disbandGroup()` 用 `members`（**当前筛选后**的 `orderedItems`）取 id：视图选「电影」而聚合里混着
一条剧集成员时，只会搬走电影那几条，剧集那条仍 `parent_id` 指它 → `child_count` 归不了零、
聚合区收不起来，而文案却说「全部成员」。修法：新增 `allChildren()` 用**无筛选参数**的
`getMediaList({ mediaType: "all", … })` 现取全量子级；取数失败**不发请求**、把原因写进聚合区；
确认文案的 N 用真实条数并注明有几个在当前筛选外。

### 6. 「加入聚合」候选漏了**祖先**方向

`addCandidates` 只用 `subtreeOf(自己)` 挡后代，没挡祖先 → A→B→C 三层、打开 B 的详情时下拉里
会出现自己的父 A，点「＋」必然被后端按 Cycle 拒，等于给了一条 100% 失败的出路。修法：新增
`ancestorsOf(id)`（沿 `parent_id` 上溯、`seen` 防环、父已删即到顶）并入 `blocked`，
`addMember` 再补一道同向兜底。

### 7. 撤销 replay 会写出悬挂 `parent_id`（Rust）

`media` 刻意没有外键（`store/schema.rs`），完整性全靠应用层；但「删 media 行」有多条路
（批量删除 / 重新识别 / 扫描收编）绕过 `delete_nodes_sync` 的「子级过继给祖父」，而撤销栈是
**进程内**的、删除时不清栈。`undo_tree_op_sync` 的 Reparent 分支是**裸 UPDATE**，
`UPDATE ... WHERE id = ?` 对已删的行静默影响 0 行，却会把 `parent_id` 写回**已删的旧父** ——
凭空造出一条悬挂引用（卡上还留着「解除分组」，详情页显示 `#<已删id>`）。修法：逐行校验存在性，
被搬的行已删就跳过、旧父已删就退回顶层，并在提示语里说清"恢复了几条、几条已被删除"。

### 8. 成环批会让 `move_nodes_sync` 空转（Rust）

一批 id 互相构成环时 `tree::roots_of` 一个都不返回，原实现会带着**空名单**继续往下走：
把目标同级整体重排一遍，再用空名单拼出「已把「」移到…」的假成功。修法：`movers` 为空直接
明确报错，并提醒用户先把其中一条挂回顶层。

## 六、未做的取舍

- 触摸设备**做不了**拖拽聚合（HTML5 DnD 在触摸下不可用）。要支持得另写一套指针拖拽，
  本轮不做——Windows 桌面端鼠标是主场景。
- 后端 `get_media_tree` / `copy_media_node` 保留（仍有单测、属通用能力），只是没有 UI 入口。
- **遗留风险（本轮未修，已记录）**：
  1. `item.depth` 的占位列在 `ITEM_COLUMNS` 里是 `0`，真实值靠 `attach_depth()` 覆盖；将来若有人新加一条**直接 `map_item` 而不调 `attach_depth`** 的查询路径，会静默拿到 `depth = 0`，前端会当真实值用（表现为层数判定偏宽松）。
  2. 「删 `media` 行」仍有 5 处裸删（重新识别 ×2、扫描收编 ×3）没走 `delete_nodes_sync` 的「子级过继给祖父」。撤销 replay 这一头已经堵住（见第四节 7），但**没有外键的 `parent_id` 仍可能被这些路径留下悬挂引用** —— 建议后续把删除收敛成一个入口。
  3. 成环脏数据（a 的父是 b、b 的父是 a）：`utils/tree.ts::buildTree` 两个节点互相当父 ⇒ **0 个根** ⇒ 封面墙整片走进「媒体库还是空的」空态。不死循环、不抛错，但整墙消失比少显示一条更糟。后端 `validate_drop` 不会造出环（已有单测），所以只有脏库 / 外部改库可达。
  4. `armDrag` 的 `releaseDrag` 是每组件一个槽位：多指针（双指）先后按在两个把手上时，先松的那一指会通过 window `pointerup` 把后一指的格复位。桌面 HTML5 拖拽是单指针、触摸下不交给原生拖拽，判断实际不可达，未写用例。

# 补记：拖放接收条件 / 顶层排序（2026-10-10 下午）

上一节交付后，实测仍有两个问题：**拖放显示禁止光标**、**列表排序失效**。
根因与修法如下。

## 一、排序失效（根因已用真实库实证）

`PosterGrid.vue` 里 `orderedParents` 用来判断"某个父级桶里有没有真实次序
（`sort_order > 0`）"，有则用 DB 的 `sort_order` 当同级次序，否则用列表下标。
**它把顶层（`parent_id` 为 null）也算进去了。**

真实库实测（`%APPDATA%\com.example.media-manager\media.db`，64 条）：

- `parent_id` 全为 NULL；
- `sort_order` = `0,3,4,5,6…63` —— 近乎全局递增的流水号。

于是"顶层桶里存在 `sort_order > 0`"恒成立 → 整面墙改用 DB `sort_order` 排序 →
`buildTree` 对同级按 `sort_order` 重排 → **墙上顺序恒等于 DB 顺序，
用户选的「名称 / 年份 / 添加时间」被整个覆盖**。

**修法**：`orderedParents` 刻意排除顶层，顶层恒按列表下标（即展示排序算出的先后）。
组内（有父）该用 `sort_order` 还用，详情页 ↑↓ 的手工次序不丢。

## 二、拖放被判定为"不可接收"

浏览器判"这个目标接不接收"看的是**事件有没有被取消**，与界面自己怎么判无关：

1. **`dragenter` 与 `dragover` 两个都要 `preventDefault()`**。原实现只挂了
   `dragover`，进入目标的那一次 `dragenter` 没被取消，该元素在这一轮里被判成
   不接收，光标直接是禁止 —— 后面每次 `dragover` 判了合法也没用。
2. **`preventDefault` 不能条件化**。原来只在"合法"时取消，非法时干脆不取消，
   等于把"这次不允许"表达成了"目标不可接收"，两种失败混成一个症状。
   正确做法是**恒取消**，用 `dropEffect`（`move` / `none`）表达能不能放。
3. `dropEffect` 必须与 `effectAllowed`（`move`）同族，否则浏览器照样画禁止光标。
4. 载荷补一个自定义类型 `application/x-media-manager-ids`，与 `text/plain` 各写一份：
   目标侧的"接收条件"与源明确对齐，`text/plain` 那一份是给 Firefox 的（不
   `setData` 根本不起拖）。
5. 聚合模式下给 `.cell` 加 `user-select: none`：卡片标题可选，按住一拖会被浏览器
   当成**文本拖拽**，光标同样是禁止、放下也什么都不发生，极像"目标拒绝接收"。

「放回顶层」区同样补了 `dragenter`。

真正的拦截仍然在 `onDrop` 的二次判定 + 后端 `commands/tree.rs`，前端规则不当安全边界。

## 四、补齐：删除路径统一「子级过继」（2026-10-10 下午）

### 问题

`media.parent_id` 刻意**没有外键约束**（层级规则在应用层校验）。因此删父节点
必须先把子级过继出去，否则会留下一串指向已删行的孤儿：它们在封面墙上永远不显示，
详情页却还挂着「脱离聚合」按钮、显示 `#<已删id>`，用户既看不见也改不了。

之前**只有** `delete_nodes_sync`（单条 / 批量删除）做了过继，另外三条路是裸删
`media` 的：

| 路径 | 位置 |
| --- | --- |
| 扫描收编散落行 | `core/scanner.rs::drop_scattered_row` |
| 单集改挂后删原独立条目 | `core/scanner.rs`（`insert_episode` 之后） |
| 清「空壳」重复剧集行 | `core/scanner.rs::drop_empty_series_shells` |
| 重新识别：电影→剧集 / 剧集→电影 | `commands/media.rs` 两处 |

`commands/tree.rs::undo_tree_op_sync` 的注释里早就抱怨过这件事
（"条目会被别处删掉…不走『子级过继给祖父』那条路"）。

### 做法：规则抽到纯函数，两个方向共用一份

- `core/tree.rs::plan_adoption(edges, doomed) -> Vec<(子级 id, 新父 id)>`——纯规则、
  可单测。判据：子级挂到**最近的不在删除名单里的祖先**；祖先全在名单里 → 顶层；
  **父链成环**（老数据被改脏）→ 一律顶层，绝不挑一个"不在名单里的子孙"当新父
  （那会造出自己挂自己，比孤儿还难查）；子级自己也要被删 → 不出现在方案里。
  ⚠️ 必须把整条父链**走到底**再回答案，不能一遇到"不在名单里的"就停——
  成环判断依赖这一点。
- `commands/tree.rs::adopt_children(conn, doomed)`——取边表 + 套规则 + 落地 SQL。
  `delete_nodes_once` 改为调用它（在事务里）；`commands/media.rs` 两处在删之前调它。
- `core/scanner.rs` 有自己的 `adopt_children`：`core` 不能反向依赖 `commands`
  （分层红线），所以自己落地 SQL，但**规则只有一份**（同样调 `plan_adoption`）。

### 存量自愈

删除路径改好了管不了**已经存在**的孤儿。`store/schema.rs::heal_orphan_parents`
在 `migrate` 末尾执行一次幂等清理（挂 `parent_id` 指向已删行 → 清成顶层），
第二次必然改 0 行，所以可以常驻。

### 前端边界

- 「所属聚合」取不到父条目时（被删，或被当前类型 / 分类 / 关键字筛选挡住），
  不再显示一个**可点的** `#id` —— 点进去必然失败。改成不可点的灰字 + 说明，
  出路是旁边的「脱离聚合」。判据复用 `parentTitle` 的查找结果，两边一把尺子。
- 「取消聚合」取全量成员、`↑↓` 按全量同级序算落点，这两条已在上一轮修好，
  本轮无改动。
