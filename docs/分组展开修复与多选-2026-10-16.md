## 一、🔴 「展开一个项目，后面那个也跟着展开」的真根因

### 结论：**不是逻辑 bug，是布局 bug**

先排除了逻辑层：`expanded` 集合**完全正确** —— 点 A 只加 A，不会碰 B。
（jsdom 探针实测：折叠 B 再展开 A，`ids=[1,11,12,2,3]`，B 的子项 `21/22` 没出现。
这条已固化成 `PosterGrid.expand.spec.ts` 的用例。）

真正的成因在 CSS 网格：`.grid` 是 `repeat(auto-fill, minmax(min(var(--card-min),100%),1fr))`，
而 `.cell` 与 `.groupbar` **都只是普通的 grid item**。于是「展开 A」之后，
A 的子项会和紧跟其后的顶层项目 B **挤在同一行**：

```
修复前（真实浏览器 Edge + CDP 量到的坐标，1100px 视口 / 6 列）
  cell        id=1    y=0    x=0     ← 顶层 A（展开）
  groupbar            y=302          ← A 的「子项」提示条
  cell child  id=11   y=334  x=0     ← A 的子项
  cell child  id=12   y=334  x=185   ← A 的子项
  cell        id=2    y=334  x=370   ← ⚠️ 顶层 B 混进了 A 的子项那一行
```

B 被画在 A 的子项**旁边**，看上去就属于 A 的展开结果 —— 用户的原话「后面紧紧跟着的
那个项目一起展开」正是这个视觉现象。

### 修法：闭合分割线（一个元素同时解决两件事）

在每个「已展开分组」的**最后一个后代**之后插一个跨整行的 `.groupend`：

| 作用 | 机制 |
| --- | --- |
| ① 用户要的「分割线」 | 它自己就是一条实线分割线 |
| ② **消除这个 bug** | `grid-column: 1 / -1` 跨满所有列 → **必然换行**，后面的顶层项目从此另起一行 |

只对**最外层**（`depth === 0`）的展开分组算：嵌套分组的子项都落在同一个外层分组里，
再画多条线只会把墙切碎。

⚠️ 分割线用**实线**（`--border-strong`）而不是分组条那种虚线：虚线表示"以下是这一组的成员"，
实线表示"这一组到此为止" —— 画成一样用户分不清哪个是开始、哪个是结束。

### 真实数据 + A/B 实证

用**用户真实库**（复制自 `%APPDATA%\com.example.media-manager\media.db`，
66 条 media / 4 个真实分组）跑真实浏览器：

```
全部收起：cells = 66, groupends = 0
只展开第一个分组（14117 宫崎骏，29 个子级）：
  y=0      ["id14117"]                                    depths=["0"]
  y=284    ["BAR"]
  y=316..1483  七个整行、每行 7 个            depths=["1"]   ← 子项独占，没有混层
  y=1783   ["END"]                                        ← 闭合分割线
  y=1800   ["id14137","id14138",...]                       depths=["0"]   ← 后面项目另起一行
  y=2092   ["id14144",...,"id14152","id14183"]             depths=["0"]
✅ 没有任何一行把「子项」和「顶层项目」混在一起 —— bug 已修
```

**可逆 A/B**（把 `.groupend` 用 `display:none` 藏掉，其它一切不变）：

```
A) 有分割线          ：混层的行数 = 0
B) 藏掉分割线（等价删掉）：混层的行数 = 1   ← bug 立刻回来
C) 恢复分割线        ：混层的行数 = 0
```

这条 A/B 是**因果证据**：分割线正是消除该现象的原因，不是碰巧。

## 二、一键展开 / 一键收起

- `PosterGrid.vue` 新增 `expandAll()` / `collapseAll()`，经 `defineExpose` 交给父级；
  并暴露 `expandedCount` / `groupCount` 给顶栏判断按钮可点性。
- `App.vue` 顶栏加「⊞ 全部展开」「⊟ 全部收起」两个按钮（放在排序旁边 —— 都是
  "改变列表怎么看"的展示操作，与右侧「新建 / 导入 / 扫描」的数据操作分开）。
  没有分组 / 已经全展开时置灰，避免点了什么都不会发生的按钮。

🔑 **两个方向都必须同步维护 `collapsedByUser`**（这是最容易漏的一点）：
- `collapseAll()` → 记下**全部**分组。否则封面墙那段「新出现的分组自动展开」的 watch
  会把刚收起的分组立刻弹回来，用户觉得按钮没用；
- `expandAll()` → **清空** `collapsedByUser`。否则下一次列表刷新会把手动折叠过的
  分组又收回去。

两条都有专门用例（`collapseAll 之后列表刷新：分组不会自己弹开` / `expandAll 之后列表刷新：分组保持展开`）。

## 三、Shift 多选 / Ctrl 多选

### 分层

- `src/utils/selection.ts`（**零依赖纯函数**）：`toggleOne` / `extendRange` / `resolveClick`。
  27 条用例覆盖：anchor 为 null / 不在 order 里、order 为空、不原地改数组、
  base 里 order 之外的残留项保留、重复 id 只认首次下标、稳定顺序、
  Shift 是**并入**且 anchor 保持不变、Ctrl 与 Cmd(meta) 同义、shift+ctrl 时 shift 优先。
- `mediaStore.selectWithMods(id, mods)`：算新集合，锚点 `selectAnchor` 存在 store 里
  （勾选集合本来就归 store，锚点是它的伴生状态；放组件里会在「详情页返回 / 换栏目并重挂」时丢掉）。
- `PosterCard.vue` → `PosterGrid.vue` → `App.vue` 一路把**修饰键**带上去。

⚠️ **`select` 事件的载荷从 `id: number` 改成了 `{ id, mods }`**（有意的破坏性变更）：
修饰键只有点击事件知道；Shift 区间还需要"上一次点的哪张"，那是父级的状态，
所以组件只如实上报「点了谁、按着什么键」。

🔑 **区间按 `visibleItems()`（当前看得见的顺序）算**，不是全库顺序 ——
用户划的永远是屏幕上那一段，换栏目 / 敲关键字后的顺序才对得上。
有一条用例专门把拼音序与 id 序**反过来**，断言区间取的是可见顺序。

**语义**：普通点击与 Ctrl+点击都是「切换这一张」（保持原有行为，不改成单选）；
**Shift+点击 = 把锚点到这一张的整段并入**选中（不是替换），且锚点保持不变，
所以连续 Shift 可以从同一原点反复调整这一段（文件管理器手感）。

### 「按住 ctrl 滑动多选」这条怎么落地的

用户还说了「按住 Ctrl 滑动多选」。现状是：
- 滑动多选（按住划过连续勾选）在**「选择」模式**下本来就可直接用，**不需要按 Ctrl**；
- Ctrl+点击 = 单张切换；Shift+点击 = 区间。

所以「Ctrl 滑动」其实已被覆盖 —— 进入「选择」模式后直接划过即可，且比按着 Ctrl 更顺手。
**若你确实要求"必须按着 Ctrl 才能划过勾选"**，那是一条独立的新交互（要在
`useSwipeSelect` 里加修饰键门槛），请明确说，我再补。
