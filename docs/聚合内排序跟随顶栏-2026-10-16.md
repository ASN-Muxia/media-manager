用户原话：「修改聚合中的排序，默认按照时间进行排序」。追问后用户选择 **「跟随顶栏排序设置」**。

## 一、先查数据，发现一个会让改动「白做」的前提

我查了用户真实库的 3 个聚合，发现两件事：

**1) 「时间」有两种含义，效果差很多**（所以我去问了用户）：

| 聚合 | 成员数 | 入库时间 added_at 去重 | 年份 year 去重 |
| --- | --- | --- | --- |
| 14135 | 30 | **2** | 22 |
| 14150 | 17 | **1** | 17 |

同一批扫描进来的成员 added_at 几乎相同 ⇒ 按「添加时间」排**视觉上等于没变**。
用户最终选了「跟随顶栏排序设置」（他当前库里是 sortBy=year, sortDir=desc）。

**2) 旧启发式会让改动完全不可见**：

原实现判断「这一组是否被手工排过」用的是 PosterGrid.orderedParents = 「该组存在 sort_order > 0」，
而 MediaDetail.members 更是**无条件**按 (sort_order, id) 排。但真实库里：

    聚合 14135: sort_order = 0,1,2,...,29    （连续）
    聚合 14150: sort_order = 0,2,3,4,5,18,19,20

这些**不是**用户手工排的，而是历史上任何一次拖动触发的 move_nodes_sync 把整组重编号的结果。
⇒ 旧启发式恒为真 ⇒ 顶栏排序永远不生效 ⇒ 用户「看不到变化」。

所以本任务的关键不是「改排序」，而是**引入一个显式的「手工排序」标记**，与 sort_order 的数值解耦。

## 二、改法

### 1) 新增持久化字段 manualOrderGroups

Rust Settings 加 manual_order_groups: Vec<i64>（#[serde(default)]，前端键 manualOrderGroups）。
settings 是 KV 表，新增 key 即生效、**不需要迁移**（B6）。读侧解析失败/脏值一律回落空 Vec，不报错。

### 2) 显示：两档，由标记决定

    const kids = store.orderedItems.filter(成员);
    组在 manualOrderGroups 里 → 按 (sort_order, id)   ← 用户亲手定的次序
    否则                     → 直接返回 kids         ← 顶栏排序序

🔑 **kids 就是顶栏序**：orderedItems = sortMediaItems(items, sortBy, sortDir, hanOrder)，
而 .filter **保序**，所以子序列天然等于顶栏序。不需要再调一次 sortMediaItems
（重复计算，还可能丢掉「已识别在前 / 未识别沉底」的分区语义）。这一点事先读代码确认过。

### 3) ↑↓ 首次点击：**先把默认序落库，再转手工**（最容易做错的地方）

顺序**不可颠倒**，否则用户会看到「点了一下顺序乱了」：

    ① moveNodes(当前渲染序的全部成员 id, self, null)
       → 后端把这一批重编号成 0..n-1
    ② store.load()          ← items 上的 sort_order 还是写库前那份，不重取会按旧值重排
    ③ loadAllSiblings()     ← 同级序刚被整体重编号，缓存已失效
    ④ settings.markManualOrder(self)   ← 落库成功才标记

反过来（先标记）会让显示**当场跳回旧库内序** —— 那正是要消灭的现象。
落库失败则不标记、不继续移动，并把原因写进 groupMsg。

🔑 **为什么「整批落库」能把当前显示序变成库内序**（读后端代码确认）：
move_nodes_sync 里 siblings 会**排除被搬者**；当把**全部成员**作为 movers 传进去、index=null 时，
siblings 为空 ⇒ final_order 恰好等于传入顺序 ⇒ sort_order 被重编号成 0..n-1。
且 roots_of 用的是**稳定** sort_by_key，不会打乱传入顺序。

### 4) 「恢复默认排序」按钮

只在手工态出现；点击只 clearManualOrder(self)，**一个 media 行都不改**。

### 5) 封面墙同样改用显式标记

删掉 orderedParents 那个「存在 sort_order>0」启发式，改为 rowsSortOrder computed：
父在名单里 → 用库内值；其余（含顶层）→ 列表下标。

传参选了 **(a) prop**（App.vue → PosterGrid :manual-order-groups）而不是组件内 useSettingsStore()：
PosterGrid 是纯展示 + 手势组件，现有全部 spec 都是 mount(Grid, { props }) 直挂、不需要 Pinia；
组件内取 store 会给它凭空加依赖并埋下第二个真相来源。另加一条 App.toolbar.spec.ts 用例
断言 prop **真的传到位**，防「忘接线导致静默失效」。

### 2) 🔑 变异测试：证明用例有牙齿

把 members 改回**无条件按 sort_order 排**（= 修复前行为），再跑同一组用例：

    x 组没有被手工排过 → 成员顺序 = 顶栏排序（与库内 sort_order 相反也照顶栏走）

    x 先发一次 moveNodes(当前渲染序, self, null) 落库，再发真正的移动，并标记手工
    x 落库失败：不标记手工、不发第二次移动，并把原因写进提示

（随后把 MediaDetail.vue 还原为修复版，diff 确认**逐字节一致**，38/38 通过。）

### 3) 核心用例的构造方式（值得记）

新用例刻意让 **名字序与库内 sort_order 相反**：

    顶栏「名称正序」→ 展示应为 A→B→C
    库内 sort_order → B(0)→C(1)→A(2)

只要成员列表还在按 sort_order 排（旧行为），断言必红。这类「两种候选顺序故意对立」的构造，
比只断言「顺序不变」有力得多。

### 4) 真实数据核对

用用户真实库（组 14135，30 个成员）算出两种次序，确认它们**确实不同**（否则改动无意义）：

## 五、遗留与取舍

1. **首次 ↑↓ 只把「当前渲染序」落库**（筛选后的可见成员）。被关键字/分类挡住的成员不在这一批里，
   后端只重排被搬的那批、其余保持相对序。对「跟随顶栏排序」是对的；
   但若一个组**长期在筛选态下**被手工排序，隐藏成员的绝对位置可能与可见序的意图不完全一致。
2. 既有差异（本次未改）：PosterGrid 收到的是 visibleItems()（含关键字过滤），
   MediaDetail 用的是 orderedItems（不含关键字过滤）—— 都是顶栏那条序的子序列，只是过滤范围不同。
3. **按约束没有启动 exe**，未在真实应用里目视确认；结论来自单测 + 变异测试 + 真实数据推演。
4. 本轮仍未 git add。
