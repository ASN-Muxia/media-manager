## 一、调研方法与样本选取

### 1.1 关键词组（3 组，用于交叉检索）

| 组 | 关键词 |
| --- | --- |
| A | `open source media server / self-hosted media manager library metadata` |
| B | `movie TV show library scraper NFO manager desktop cross-platform` |
| C | `影视库 刮削 整理 媒体库 开源 NAS 本地播放器` |

### 1.2 抽样原则

1. **必须是真实开源**：有官方仓库、可读的 LICENSE 文件，能在检索日取到源码/manifest；
2. **必须与本项目相关**：与「本地影视资源录入、分类、检索、管理、播放」任一段相关；
3. **优先取成熟度与活跃度较高者**，同时对「技术栈相近但已停滞」的样本保留并标注风险（如 Dim）。

### 1.3 关于 Plex / Emby 的边界声明（重要）

| 对象 | 开源状态判定 | 依据（核验于 2026-10-04） | 本报告的处理 |
| --- | --- | --- | --- |
| **Plex** | **非开源**（无官方开源服务端仓库） | GitHub 官方组织 `plexinc` 存在（仅有客户端类仓库，如 `plexinc/plex-media-player` 返回 200）；服务端仓库地址 `plexinc-pms` 返回 **404** | 不作为调研对象；其交互参照价值通过开源替代品间接吸收 |

### 2.1 跨项目的共性结论（用于后文对比的"功能坐标系"）

| 共性 | 说明 | 代表证据 |
| --- | --- | --- |
| **元数据回落有多源优先级** | 权威源 → 补充源 → 可选增强；缺才补、不覆盖 | 本项目 `provider/mod.rs` 已有同构约定；TMM README 多源列表；Jellyfin 多provider |
| **本地文件证据优先于远程 guess** | Kodi：本地 NFO → 在线刮削；本项目：结构证据 > 时长 | https://wiki.kodi.tv/view/NFO_files ；`core/mediatype.rs` 头部注释 |
| **`.nfo`（或等价 sidecar）是跨系统互通介质** | TMM/MediaElch 写 NFO；Kodi/Jellyfin/Emby/Plex 读 NFO | TMM README；MediaElch README；Kodi wiki |
| **观看状态 / 续播是资源管理的标配** | 播放历史与续播点对应着"管理自己的影视库"而非"只是文件列表" | Jellyfin https://docs.jellyfin.org/ ；Stash 有 Settings→任务 |
| **可扩展性通常做成"provider 注册表 / 插件"** | Stash 社区 scraper 可在线装；Jellyfin 插件隔离加载；Kodi add-ons | Stash README + CommunityScrapers；jellyfin-plugin-template |
| **技术参数（codec/时长/分辨率）值得抽取进库** | TMM 明写"extracted from each media file" | TMM README |
| **中文全文检索需要专门分词** | MoviePilot v3 自带 `native/fts5_cjk` | MoviePilot v3 仓库树 |
| **API-first 是走向多端/自动化的前提** | Jellyfin / Stash / MoviePilot 均先有 API 再多端 | 各项目 README/文档 |

### 3.2 已具备的能力（这也是"必须保持"的清单来源）

- 扫描：递归遍历 → 解析 → 入库；后台线程 + `scan-progress` 事件 + `cancel_scan` 可取消（`src-tauri/src/commands/media.rs:26` 及 `App.vue:306-326`）
- 文件名解析：扩展名清单（本机 D 盘实测依据 `docs/scan_exts_d.json`）+ **文件头 magic number 兜底**（`src-tauri/src/core/parser.rs:20-56`，见 `VIDEO_EXTS` 与 `VideoContainer`）
- 类型判定：**R0–R12 多信号打分**，可配置，`Unknown` 是一等公民，**结构证据优先于时长/体积**（`src-tauri/src/core/mediatype.rs:1-77`）
- 剧集分组与二次校正 + `locked` 锁定（ `src-tauri/src/core/grouping.rs`；`db.rs` v4 备注）
- 系列电影合集：视图级聚合 + 无损去重（同标题同年份留信息最完整一条，其余进 `duplicates`）（`src-tauri/src/core/collection.rs:1-35`）
- 树形组织：`parent_id` / `sort_order`（schema v5），`MAX_DEPTH=4`，环/深/自身/缺失四类错误校验，移动 / 另存为 / **撤销栈**（`src-tauri/src/core/tree.rs`、`src-tauri/src/commands/tree.rs`）
- 元数据刮削：**TMDb → TheTVDB → Fanart.tv → OMDb → 豆瓣（中文兜底）→ 大模型**；LLM 只解析脏文件名，**失败回退正则、绝不替代元数据 API**（`README.md` §四b、`src-tauri/src/provider/mod.rs:1-8`）
- 分类 / 标签：`categories`（`kind` + `origin` + 大小写不敏感唯一）+ `tags`，各自多对多关联；支持从 TMDb 同步分类（`db.rs:98-132`；`commands/catalog.rs`）
- 检索：后端 SQL `LIKE ... ESCAPE '\'`（转义 `%` `_` `\`）命中标题/原名/genre/group_key/年份；前端可视项二次过滤（`src-tauri/src/commands/media.rs:660-685`；`src/stores/mediaStore.ts`）
- 详情编辑 / 新建：`createMedia` / `updateMedia`，手动新建剧集与扫描结果同库同构（README §四 第 7 条）
- 指定归属：`import_folder_into`（`86版西游记.01.mkv` 类推断失效场景的显式入口）——修复记录见 `docs/交接状态-2026-09-25.md` §17.12
- 播放：优先 PotPlayer（7 个候选路径自动探测），未装则回退系统默认；"在文件夹中显示"（`src-tauri/src/commands/play.rs:11-89`）
- 任务反馈：扫描 / 刮削各有进度条（含总数未知时的**不确定态动画**）与停止按钮（`src/App.vue:306-340`）
- 本地优先：数据落在 `%APPDATA%\com.example.media-manager\media.db`，无云、无遥测、无服务端
- 工程质量：`cargo test` / `vitest` / `tsc --noEmit` 全套，`verify.bat` 一键盘点

## 五、不可变核心边界（Immutable Core Boundary）

> 以下 8 条是让这份调研"只做增量"的锚点。任何架构方案如果违反其中一条，即为不合规。

| # | 边界 | 为什么 | 证据锚点 |
| --- | --- | --- | --- |
| B1 | **主体主流程不得改变**：扫描/导入 → 文件名解析 → 类型判定 → 元数据刮削 → 分类标签 → 检索浏览 → 详情 → 播放 | 这是用户每天走的路径，改变等于重写产品 | `README.md` §四 使用流程；`App.vue` 视图切换逻辑 |
| B2 | **本地优先、单机桌面、默认无网络暴露** | 用户的数据在自己的机器上；不得引入强制联网或云依赖 | `db.rs`（SQLite@APPDATA）；`Cargo.toml`（无 server） |
| B3 | **四层分层不反向依赖**：`core` / `provider` / `store` 互不依赖，只有 `commands` 同时使用三者 | 这是本仓最值钱的结构资产，替换 UI 或 DB 都不用碰领域规则 | `lib.rs:1-9` |
| B4 | **类型判定规则集中在 `core/mediatype.rs`，可配置；`Unknown` 是一等公民；结构证据优先于时长/体积** | 该项目历史上多次误判的根因治理成果，不得退回"单 Rule + 默认电影" | `core/mediatype.rs:1-77`；`core/parser.rs` 实测依据 |
| B5 | **元数据 API 权威，LLM 只做脏文件名补漏，失败即回退，不得替代元数据 API** | README 已明文承诺（"不得以纯 AI 刮削替代元数据 API"） | `README.md` §四b；`provider/mod.rs:1-8`；`provider/llm.rs` |
| B6 | **数据库只能增量迁移，绝不重建库、绝不要求用户重新导入** | `user_version` + `ensure_column` 的升级路径已被单测锁死，且用户库里有真实数据 | `db.rs:171-225`（v1→v5）；5 个迁移单测用例 |
| B7 | **既有的幂等/去重语义不得破坏**：`file_path` 唯一索引 upsert、`group_key`、`locked`、`source`（scan/manual） | 否则会在重扫时把用户手工整理好的条目冲掉 | `db.rs:89-95`、`db.rs:194-202`；`core/grouping.rs` |
| B8 | **Tauri 命令契约与前端 stores/components 结构不整体换掉** | 前端 3 个 store + 9 个组件 + 全套 spec 已在跑（`cargo test` 数百例 / `vitest` 上百例），重构收益远低于风险 | `lib.rs:54-124`；`src/stores/*`；`src/**/*.spec.ts` |

## 六、增量机会清单（P0 / P1 / P2）

> 口径：**P0 = 本次架构必须为其预留位置且应尽快落地**；**P1 = 应尽快补**；**P2 = 有价值但可延后/需先用户确认**。
> 每条都标注了「**落地方式必须增量**」的具体边界，避免变成重写。

### P0（本次架构必须支持）

| ID | 机会 | 解决什么 | 借鉴来源 | 增量落地约束 |
| --- | --- | --- | --- | --- |
| **P0-1** | **元数据结果本地缓存层** | README §八 已列："TheTVDB / Fanart.tv / OMDb 与大模型的调用结果没有本地缓存，重复刮削会重复请求" | TMM / Stash 均有本地元数据缓存 | 加在 `provider` 层**旁路**：新增 `store` 侧缓存表 + `provider/http.rs` 的读缓存；**不改动现有 provider 函数签名与优先级顺序**；缓存 miss 行为与当前完全一致 |

| **P2-4** | **ffprobe 抽取技术参数** | `resolution`/`duration` 现在由文件名猜（LLM），不是实测 | TMM "extracted from each media file" | 需要引入 ffprobe 二进制依赖，重量级；涉及 Windows-only 打包 |

| **P2-6** | **字幕下载与管理** | 完全缺失 | TMM（OpenSubtitles）/ Jellyfin opensubtitles 插件 | 外围能力，取决于 P2-4 是否引入 ffprobe |
| **P2-7** | **自动改名 / 整理** | 完全缺失 | TMM 改名模板 / Sonarr-Radarr renamer | **高危写磁盘操作**，必须先有 dry-run 与完整撤销，且需先确认用户是否有此诉求 |
| **P2-8** | **跨平台（Linux/macOS）** | 播放桥接与打包都是 Windows 专用 | Jellyfin / TMM / Kodi | 依赖播放器抽象与打包链重构，与 B2 无冲突但工作量大 |

## 八、仍有不确定之处（请 team-lead / 用户裁决）

1. **是否要上「自动改名 / 整理」（P2-7）**：竞品普遍有，但它是唯一会**写用户磁盘**的能力。当前既无此项也无明确用户诉求证据，倾向保留在 P2 并先确认意图。
2. **是否要走「内置播放器 / 转码」（P2-5）**：这是与竞品差距最大的一块，但也是工作量与维护成本最高的一块。若用户的真实诉求是"本地播放"，则更划算的路径是先把 Jellyfin 式的播放状态补齐（P0-2）与连播（P1-6），而非自研播放器。
3. **是否要走向服务化（P2-1 / P2-2）**：一旦做就会触碰 B2（本地优先）。我的建议是**可以预留，但本期不启动**；请确认用户是否真的需要多端。
4. **Emby 的定位结论**为弱证据（见 §7.1），若后续需要引用其特性，需单独核验。
5. **两个单项的结论依赖产品口径**：
 - `SourceHint`（R1，数据源明确类型时的优先级最高）目前在命令层是否真的接上了，需要架构师确认——它影响 P0-4/P1 的实现顺序。
 - `resolution` / `duration` 是否当前就已经有实测来源，还是纯粹靠文件名与 LLM。代码注释写明 `resolution` "正则解析不产出"（`db.rs:200-201`），由此推断**缺少 ffprobe 实测管线**，建议架构师确认后决定是否纳入 P2-4。
