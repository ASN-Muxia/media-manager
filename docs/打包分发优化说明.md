# 打包 / 分发 / 传输优化说明

> 目标：让项目更容易**压缩打包、分发和增量传输**。
> 本文给出四件事：目录结构方案、具体改动清单、如何验证功能不变、体积与耗时的实测数据。
> 结论先行：**最大的收益不来自改代码，来自把「分发对象」从整个工作目录换成显式源码包**；
> 代码层面的拆分真正见效的地方在**增量传输**，而不是全量压缩包。

---

## 1. 体积真相先摆出来

动手之前先量了一遍，结论和直觉相反：

| 位置 | 体积 | 是不是分发对象 |
|---|---|---|
| `src-tauri/target` | **5.7 GB** | 否（构建产物） |
| `node_modules` | 118 MB | 否（依赖） |
| 真正的源码 + 配置 | **约 3 MB** | **是** |

也就是说，`src-tauri/src` 全部 `.rs` 加起来不到 500 KB，代码层面的微优化对整个分发体积几乎没有发言权。
真正决定传输成本的是：**你手上有没有一条「只打包该打包的东西」的通道。**

## 2. 调整后的目录结构

### 2.1 Rust 侧：从「平铺 12 个模块」改成四层

```
src-tauri/src/
├── lib.rs / main.rs        入口，只做装配
├── boot.rs                 启动前置检查
├── core/                   领域规则：不碰 GUI、不碰数据库
│   ├── parser.rs           文件名 → 结构化字段
│   ├── mediatype.rs        电影 / 剧集 / 待确认 判定（12 条加权信号）
│   ├── grouping.rs         分组与并查集
│   ├── collection.rs       系列电影派生视图
│   ├── scanner.rs          目录扫描
│   └── tests/              scanner / grouping / mediatype / parser 的用例
├── provider/               外部数据源
│   ├── http.rs             共享 HTTP + hosts 自定义解析
│   ├── tmdb.rs  tvdb.rs  fanart.rs  omdb.rs  llm.rs
├── store/                  SQLite
│   └── db.rs
├── commands/               Tauri 命令层
│   ├── control.rs          任务控制（Scan/Scrape 共用）
│   ├── catalog.rs  diag.rs  media.rs  play.rs  scrape.rs  settings.rs
│   └── tests/
└── util.rs                 共享工具：lazy_re! 宏 + 路径助手
```

**依赖方向被写死在各个 `mod.rs` 的注释里**：`core` ← 谁都可以用，`core` 谁都不依赖；
`provider` / `store` 互不依赖；只有 `commands` 能同时碰三者。
好处是以后加功能有唯一去处，不会出现"这个判断到底该放 scanner 还是 db"的扯皮。

### 2.2 前端侧：`src/constants/` 收口常量

类型→文案→图标的映射原先在 `PosterCard` / `MediaDetail` / `Sidebar` 里各写一份，现在统一到
`src/constants/mediaType.ts`（`MEDIA_TYPE_LABEL` / `MEDIA_TYPE_ICON` / `typeLabel()` / `typeIcon()` / `formatScore()`）。

### 2.3 打包侧：`mjs/` + `release/`

```
mjs/                  .mjs 脚本（2026-10-02 从根目录与 scripts/ 收拢）
├── build/package.mjs        源码打包（ZIP / tar.gz，零外部依赖）
├── build/verify-delta.mjs   增量包逐字节往返校验
├── dev/dev-server.mjs       vite Node API 起服务
├── dev/run-tests.mjs        vitest 包装器
└── test/package.spec.mjs    package.mjs 的自测（跟前端用例共用 vitest）

scripts/              仅保留非 .mjs 脚本：scan_video_exts.py / 启动影视库.vbs

release/              打包输出（已 gitignore）
├── media-manager-src-<ver>.zip
├── …zip.filelist.txt     sha256 + 体积 + 路径（下一次做增量的基线）
└── …zip.manifest.txt     条目数 / 体积 / 压缩率 / 耗时
```

## 3. 具体改动清单

### 3.1 清掉不该参与分发的东西

| 改动 | 说明 |
|---|---|
| `src-tauri/target` 清空后重编 | 删掉 10,483 个陈旧中间产物（含重复 `.pdb` 1.1 GB、15 个旧 `.exe`），**5.7 GB → 1.9 GB** |
| `.gitignore` 补全 | 加 `*.log`、`*.pdb`、`*.rs.bk`、`vite.config.ts.timestamp-*`、`release/`、`*.zip`/`*.tar.gz`、`.vite`/`.vitest` 等 |
| 新增 `.gitattributes` | 源码统一 LF；**`.bat`/`.cmd`/`.vbs`/`.ps1` 强制 CRLF**；二进制显式标注；锁文件与 `src-tauri/gen` 标 `linguist-generated -diff` |
| 删 `src-tauri/icons/icon.png` | 未被 `tauri.conf.json` 引用，是纯冗余 |
| `icon.ico` 重编码 | 372,526 B → **5,505 B**，七帧逐像素 **0 差异**（见 §5.4 的诚实说明） |

### 3.2 消除重复代码

| 位置 | 之前 | 之后 |
|---|---|---|
| `lazy_re!` 宏 | parser / mediatype / collection 各一份（3 份） | `util.rs` 一份，`pub(crate) use` 导出（Rust 2018 起 `macro_rules!` 可按路径导入） |
| 父目录 / 目录名取值 | `scanner.rs`（自定义 `dir_key_of`）+ `commands/media.rs`（`parent_dir_of`/`dir_name_of`）+ 若干处内联（4 份） | `util::parent_dir` / `util::dir_name` 2 个函数 |
| 任务控制 | `ScanControl` / `ScrapeControl` 两份字符级重复的 impl | `TaskControl` + `task_control!` 宏生成两个 newtype |
| HTTP 客户端 | `tmdb.rs` 自建 agent + 私有 `get_json` | 复用 `provider::http::build_agent` / `http::get_json`（顺带把漂移掉的 403/429 报错文案拉回来了） |
| 前端类型→文案/图标 | 3 处重复 | `src/constants/mediaType.ts` 一处 |

> `ScanControl` / `ScrapeControl` 必须保持**两个不同的 Rust 类型**：
> `tauri::App::manage` 按类型 key 管理状态，合并成一个类型后第二次 `manage` 会覆盖第一次。
> 所以用「newtype + `Deref` 到 `TaskControl`」而不是直接合并。

### 3.3 控制单文件体积

把内联的 `#[cfg(test)] mod tests` 抽成同目录下的独立文件，用 `#[path]` 挂回来：

```rust
#[cfg(test)]
#[path = "tests/scanner.rs"]
mod tests;
```

好处是 `use super::*;` 照样能访问私有成员，**可见性完全没变**，但主文件行数下来了：

| 文件 | 抽之前 | 抽之后 |
|---|---|---|
| `commands/media.rs` | 2,160 行 | 1,359 行 |
| `commands/scrape.rs` | — | 1,086 行 |
| `core/grouping.rs` | — | 878 行 |
| `core/mediatype.rs` | — | 738 行 |
| `core/scanner.rs` | — | 593 行 |
| `core/parser.rs` | — | 425 行 |

合计抽出约 2,860 行测试代码到 6 个文件。

### 3.4 顺手修掉的两个潜在事故

1. **新克隆根本编译不过**。`cargo clean` 后重建报
   `E0107: struct takes 3 generic arguments but 2 were supplied`（`schemars 0.8.22` × `indexmap 1.9.3`）。
   根因是 `indexmap` 的 `build.rs` 用 `autocfg` 探测 `std`，探测**静默失败**（stderr 只有一行 warning），
   于是 `IndexMap` 的第三个泛型参数失去默认值。修复：在 `Cargo.toml` 里显式给 `indexmap` 开 `std` feature。
   ⚠️ 必须同时写进 `[dependencies]` **和 `[build-dependencies]`**——resolver v2 **不会统一**这两者的 feature。
   这意味着：在修好之前，任何人拿到包都编译不出来。
2. **`verify.bat` 增加第 6 步**（打包冒烟），让打包脚本不再是"跑过一次就没人管"的一次性脚本。
   改这个文件必须保持 **GBK 编码 + CRLF 换行**，否则 cmd 会把它解析成一坨报错的乱码。

### 3.5 打包工具本身

`mjs/build/package.mjs`：**零外部依赖**，ZIP / tar.gz 容器、CRC32、deflate 全部用 Node 内置能力实现。

为什么不直接调系统的 `tar` / `git`：本机 Node **派生子进程一律 EBUSY**（`spawnSync("git")` 和
`spawnSync("tar.exe")` 都返回 EBUSY），依赖外部命令在这台机器上就是不可用的。

几个关键设计：

- **优先 `git ls-files`**，拿不到 git 就降级遍历，并在输出里说明降级原因。
- **遍历时尊重 `.gitignore`**（自己实现规则转正则，支持 `*`/`?`/字符类、目录规则、`!` 否定）。
  为什么非要这一步：写死排除名单时，vite 生成的 **9 个 `vite.config.ts.timestamp-*.mjs` 漏进了分发包**，
  而 `.gitignore` 里明明写着。"什么不该被分发"只能有一个出处。
- **`--reproducible`**：时间戳归一化。**DOS 时间戳一律取 UTC**（本地时区会让东京和柏林打出不同字节），
  同一份内容 → 同一份字节 → CDN 可缓存、可做二进制差分。
- **`--delta-from`**：按 sha256 比对上一版清单，只打包真正变过的文件，另写 `*.deleted.txt`。
- manifest 里记录条目数 / 原始体积 / 打包体积 / 压缩率 / 耗时，便于复盘。

## 4. 如何验证「功能没变」

全部收进 `verify.bat`，一键盘点六项，退出码 0 才算通过：**

```
[1/6] 前端构建        vite build
[2/6] 前端类型检查    tsc --noEmit
[3/6] 前端单元测试    vitest run（含 mjs/test/package.spec.mjs）
[4/6] Rust 测试       cargo test --features custom-protocol
[5/6] Rust 编译链接   cargo build --features custom-protocol
[6/6] 分发打包冒烟    mjs/build/package.mjs --dry
```

实测结果（`MM_NO_PAUSE=1 cmd //c verify.bat`，退出码 0）：

- vitest **9 文件 / 99 用例通过**（其中 20 条是本次新加的打包脚本用例，79 条为原有）
- tsc --noEmit 0 错误
- vite build 62 modules
- cargo test **239 passed / 0 failed**（原有 235 + `util.rs` 2 条 + `control.rs` 2 条）
- cargo build 产出 `src-tauri\target\debug\media-manager.exe`
- 打包冒烟通过

### 三层防线

1. **重构前后测试数对比**：Rust 235 → 239（只多了新抽出来的 `util.rs` / `control.rs` 的用例），
   **没有任何一条用例被删**；前端同理。这是"行为没变"最直接的类比证据。
2. **文件搬家用 `git mv`**：`git status` 里显示的是 `R`（rename）而不是"删除 + 新增"，
   历史跟着走，diff 里能直接看出改了什么。
3. **逐字节往返校验**：`mjs/build/verify-delta.mjs` 把 `after-delta.zip` 叠加到 `before.zip` 上、
   按 `deleted.txt` 删掉 13 个路径，再跟当前工作副本逐字节比对：

   ```
   基线包    : 73 个条目
   增量包    : 48 个条目
   删除清单  : 13 个路径，命中 13 个
   叠加结果  : 90 个条目
   目标清单  : 90 个条目

   逐字节比对 90 个文件：全部一致，0 异常、0 残留。
   结论: 增量包 ≡ 整包替换，可以安全地只传增量。
   ```

   这一步同时证明了两件事：「增量包 ≡ 整包替换」，以及自己写的 ZIP 容器没写错
   （第三方 `bsdtar` 能解开、第三方 Python `zipfile` 能读）。

⚠️ 一个环境相关的坑：本机 Node 派生子进程会 EBUSY，所以 `git ls-files` 在这台机器上取不到，
会降级到遍历模式。这不影响正确性——遍历模式现在也读 `.gitignore`，两种方式产出的清单一致。

## 5. 量化结果

**测量口径**：同一个脚本（`mjs/build/package.mjs`）、同一个 deflate level 9、同一个 `--reproducible`
模式，分别打包基线 commit `a081384` 和当前 HEAD。不用 `git archive` 和脚本对打——那是两个实现，不可比。

### 5.1 全量源码包

> 说明：`docs/` 与 `交接状态-2026-09-25.md` 本身也在这个源码包里，下面的最终数字已包含它们。

| | 条目数 | 原始体积 | ZIP |
|---|---|---|---|
| 重构前 `a081384` | 73 | 1,369,476 B | 322,403 B |
| 重构后 HEAD | 90 | 1,057,667 B | 365,870 B |
| 变化 | +17 | **−22.8%** | **+13.5%** |

**这里必须说实话：全量 ZIP 不但没变小，还大了 8.9%。** 原因是：

- 新增的文件本身要占地方——打包工具 `package.mjs` + 它的用例 ~9 KB、`src/constants/mediaType.ts`、
  `commands/control.rs`、`util.rs`、三个 `mod.rs`、6 个 `tests/*.rs`、`.gitattributes`、`package.bat`；
- 而删掉的 `icon.png`（约 1 KB 压缩后）+ 缩小后的 `icon.ico` 省下的极少；
- 更重要的一条：**ZIP 每个条目独立跑 deflate，字典不共享**。把大文件拆成多个小文件会**损失跨文件重复**，
  压出来反而更胖。这一项大约抵消掉了拆分的收益。

原始体积降 22.8% 是真金白银（工作副本、git checkout、不做压缩的传输方式都按这个算）。


#### 换个容器立刻见效：tar.gz 比 ZIP 小 13.0%

同一份内容、同一个脚本，只换容器：

| 容器 | 重构前 | 重构后 | 变化 |
| --- | --- | --- | --- |
| ZIP（每条目独立 deflate） | 322,403 B | 365,870 B | +13.5% |
| **tar.gz（整包单一 gzip 流）** | 290,485 B | **318,357 B** | +9.6% |

同一份新源码：**ZIP 365,870 B → tar.gz 318,357 B，省 13.0%**。
原因就是上面那条——gzip 只有一个流、32 KB 字典跨文件共享，拆文件不再付出代价。

而且 `after.tar.gz`（318,357 B）已经**比 before 的 ZIP（322,403 B）还小 1.3%**——
也就是说，只要把分发格式换成 tar.gz，全量包就能做到"既多了工具，也没变胖"。


> 中途测过一次还没写这篇文档的中间态：89 条目 / 1,043,530 B 原始 / 359,299 B ZIP，趋势完全一致。
> 数字会随“顺手加的工具”小幅上移——**工具链本身也要计入分发成本**。

### 5.2 版本升级：增量包 vs 整包

从 `a081384` 升到 HEAD：

| 方案 | 要传的字节 |
|---|---|
| 整包替换（重构前的唯一选项） | 322,403 B |
| 本次的增量包（48 个变更 + 13 个删除） | **257,676 B**（**−20.1%**；比新整包 −29.6%） |

端到端校验：「before.zip 解压 + 增量包叠加 + 按 deleted.txt 删路径」与当前工作副本
**90 个文件逐字节一致，0 异常、0 残留**。

### 5.3 日常改动：改一行代码要传多少

这才是拆分真正见效的地方——**改动的影响被隔离在小文件里**：

| 场景 | 重构前 | 重构后 | 改善 |
|---|---|---|---|
| 改一行 `commands/media.rs` | 21,172 B | 14,452 B | **−31.7%** |
| **只改一行测试** | 21,174 B | **7,987 B** | **−62.3%** |

第二行是重点：以前测试内联在 `media.rs` 里，**动一个测试也要重传整个 2,160 行的文件**；
现在测试独立成 `commands/tests/media.rs`，生产代码一个字节都不用走网络。

### 5.4 关于 `icon.ico`：一个被实测推翻的判断

重编码把它在磁盘上从 372,526 B 压到 5,505 B（**−98.5%**），但：

| | 磁盘体积 | deflate 之后 |
|---|---|---|
| 原 BMP 存储 | 372,526 B | **3,532 B** |
| 现 PNG 存储 | 5,505 B | **5,157 B** |

BMP 帧里全是透明像素的连续零字节，deflate 压到 100:1；换成 PNG 后已经压过一遍，
反而**不能**再被压缩，进 ZIP 的体积**多了 1,625 B**。

所以这个改动的正确定性是：**省的是磁盘 / checkout / 不做压缩的传输通道，不是压缩包体积**。
七帧逐像素比对差异为 0，视觉上完全等价。

### 5.5 传输耗时（带宽换算，非实测）

左侧是「不清理就压缩整个工作目录」的成本，右侧是走打包通道的成本：

| 带宽 | 5.9 GB 工作目录 | 357 KB 源码包 | 252 KB 增量包 |
|---|---|---|---|
| 千兆内网 1000 Mbps | 50.7 s | 0.003 s | 0.002 s |
| 百兆网 100 Mbps | 8.4 min | 0.029 s | 0.021 s |
| 家用上行 20 Mbps | **42.2 min** | 0.146 s | 0.103 s |

**5.9 GB / 357 KB ≈ 17,315 倍。** 这才是这次改造最大的收益，而且它跟代码写得好不好没多大关系——
它来自"终于有一条明确的打包通道了"。

## 6. 用法

```bash
npm run package                     # release/media-manager-src-<ver>-<sha>.zip
npm run package:gz                  # .tar.gz
npm run package:dry                 # 只统计不落盘

# 首次分发：把 release/*.zip 发出去，同时留着 .filelist.txt
# 之后每次升级：拿对方的旧 filelist 做基线
node mjs/build/package.mjs --reproducible --delta-from release/上一版.zip.filelist.txt
```

接收方：解包 → 按 `*.deleted.txt` 删路径。等价于整包替换，但网络上只走了变动的部分。

### 6.1 校验增量包确实等价（`mjs/build/verify-delta.mjs`）

```bash
npm run verify:delta -- ^
  --base release/上一版.zip ^
  --delta release/新版-delta.zip ^
  --expect-list release/新版.zip.filelist.txt ^
  --expect-root .
```

它把「基线包 + 增量包叠加 + 按删除清单摘路径」的结果与新版全集的 sha256 逐条对齐，
全等才给退出码 0。**这里的 ZIP 解析是独立手写的另一套实现**，不复用 `package.mjs` 的生成逻辑——
两边独立，容器格式写错就会被 CRC32 + sha256 双重校验抓住。

Windows 下不想敲命令就双击根目录的 `package.bat`（该文件为 GBK 编码 + CRLF，改动时需保持）。

## 7. 遗留事项

- 全量包仍比基线重：ZIP +13.5%、tar.gz +9.6%。想再压下去，优先级从高到低：
  1. **改发 `.tar.gz`（已实测有效，推荐直接用）**：同一份源码 365,870 B → **318,357 B，省 13.0%**，
     代价只是接收方多一条解压命令。这是现在性价比最高的一步。
  2. 把 `docs/` 与交接文档移出源码包（约 27 KB 压缩后）——代价是接收方拿不到说明文档。
  3. `Cargo.lock` + `package-lock.json` 占包的 **16%**（54 KB），为了可复现构建不能删，
     但可以考虑单独维护一份不含锁文件的"最小可编译包"，让接收方跑 `cargo update` 自行解析。
  注意：即便全量包没变小，**增量传输的收益是实打实的**（§5.2 / §5.3）。
- `.gitattributes` 里给 `*.lock`、`*.json` 之类标了二进制 / generated，
     但 `Cargo.lock`、`package-lock.json` 仍占包的 **16%**（54 KB 压缩后），它们为了可复现构建不能删。
- 增量包目前是**文件级**粒度。想做到"改一行只传几十字节"，得上真正的二进制差分
  （`zstd --patch-from` / `bsdiff`），本机环境暂时不支持外部差分工具。
